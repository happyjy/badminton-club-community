# 회비 정산 — 자동 판정 파이프라인 정리와 납부현황 내보내기 설계

작성일: 2026-10-10
브랜치: `feat/membership-fee-on-main`
상태: 설계 승인 대기

## 1. 배경

- **이 브랜치의 목표는 재무가 통장 엑셀을 올리면 연간 납부현황표가 나오는 것이다.**
  - 밀려 내기·미리 내기·몰아 내기, 병가 면제, 부부 단가, 행사 입금이 섞인 통장을 월별로 정리하는 일이 재무의 가장 큰 부담이다.
  - 기능을 하나씩 쌓아 왔기 때문에 전체 구조를 실제 데이터로 다시 검토했다.
- **1~4월 일반 회비 흐름은 실제로 돌아갔다.**
  - 업로드 배치 4개, 거래일 2025-11-30 ~ 2026-04-30, 입금 275건 중 244건 확정.
  - 디자인 시스템 전환까지 끝났고 테스트 1718개가 통과한다.
- **5월부터는 재무가 쓰지 않았다.**
  - 마지막 업로드가 2026-05-09이고, 통장 파일(2026-01-01 ~ 10-03, 입금 649건) 중 425건이 DB에 없다.
  - 5월 이후 파일에는 지금 구조가 받아내지 못하는 패턴이 몰려 있다.

### 1.1 통장 파일 649건을 현재 로직에 통과시킨 결과

| 판정 | 건수 | 내용 |
| --- | --- | --- |
| 정상 매칭(금액 일치) | 431 (66%) | 정확 169 · 부분 247 · 부부 15 |
| 매칭됐지만 "부족" | 163 (25%) | 뒷풀이 15,000원 76건, 단체티 20,000·24,000원 61건, 부부 중 한 명 단독 25,000원 등 |
| 가입비로 대기 | 30 | 이 중 7건은 4개월 회비(100,000 = 25,000 × 4), 2건은 찬조 |
| 매칭 실패 | 11 | 통장 이자 10건(거래구분 '예금이자'), 오타 1건("최라옴") |
| 에러 | 13 | 회비+콕 합산(49,500), 51,000 등 |
| 탈퇴·거절 회원에 매칭 | 64 | 매칭 후보가 상태·시점 무관 전체 회원이라 생김 |

- **행사 입금이 회비로 들어온다.**
  - 뒷풀이·단체티 137건이 "매칭됨(부족)"이 되어 하나씩 건너뛰어야 한다.
  - 실수로 확정하면 15,000원이 그 달 회비로 잡힌다.
- **연납·합산 입금을 잘못 센다.**
  - 275,000원 연회비는 25,000 배수라 11개월로 제안된다(연납 단가 미인식).
  - 125,000원(가입비+1개월)은 5개월로 제안된다.
  - DB에 22,916원 납부가 24건 있는 것은 재무가 "부족 확정"으로 연납을 우회한 흔적이다.
- **카카오뱅크 메모는 없어질 예정이다.**
  - 메모 252건은 재무가 앱에서 손으로 적은 정산 기록(월 지정, 오타 교정, "가입비+1월", 행사 참가자 번호)이다.
  - 시스템을 쓰면 이 메모를 더 적지 않으므로, 메모가 하던 일을 시스템이 맡아야 한다.
  - 입금자명(입금자가 직접 쓴 것)에는 약 260/649건에 월이 적혀 있어 힌트로 계속 쓸 수 있다.

## 2. 목표와 비목표

### 목표

- 통장 엑셀을 올리면 회비가 아닌 건은 자동으로 빠지고, 회비는 회원·개월 수·월이 자동으로 정해진다.
- 재무는 "검토 필요" 건만 보고, 나머지는 **일괄 확정 버튼 한 번**으로 확정한다.
- 대시보드에서 **납부현황 엑셀**(첨부 이미지와 같은 모양)을 내려받는다.
- 카카오뱅크 메모가 하던 일(월 지정·오타 교정·분할·메모)을 시스템 안에서 할 수 있다.

### 비목표 (이번 범위 밖)

- 행사별 수금 현황(누가 뒷풀이비를 냈는지). 행사 입금은 분류만 하고 회비에서 제외한다.
- 출금(환불) 행 처리. 환불은 재무가 해당 월의 확정을 취소하는 기존 기능으로 처리한다.
- 분류 규칙 편집 화면. 규칙은 코드 상수로 두고 건별 수동 변경만 지원한다.
- 연중 단가 변경(FeeRate 적용 시점).
- FeeType/MemberFeeType 구조 정리. 설정 화면은 그대로 두되 새 코드는 이 구조를 확장하지 않는다.
- 업로드 시 자동 확정. 확정은 항상 사람이 버튼을 누른다.

## 3. 결정 사항

| 질문 | 결정 | 이유 |
| --- | --- | --- |
| 확정을 어디까지 자동으로 하나 | 매칭까지 자동, 확정은 버튼 한 번 | 자동 확정의 오류를 재무가 못 알아챌 위험보다 버튼 한 번이 싸다 |
| 행사 입금 | 분류만 하고 회비에서 제외 | 회비 목표에 집중. 행사 정산은 범위 밖 |
| 내보내기의 비고(직책)·임원 정렬 | `ClubMember`에 직책·정렬 순서 필드 추가 | 매번 다시 입력하지 않는다. 컬럼 추가만이라 안전 |
| 출금(환불) | 범위 밖 | 메모 없이는 구분 불가. 발생 빈도가 낮다(9개월 4건) |
| 접근 방식 | A. 정리 + 증축 | 컬럼 추가만으로 S1~S5·S8을 닫고 확정 244건과 화면을 살린다. 재설계(B)는 출금을 안 다루는 지금 비용을 정당화할 데이터가 없다 |
| 내보내기 형식 | xlsx 한 시트, 셀 색 적용 | 인쇄는 엑셀에서 |
| 월 힌트와 자동 제안이 다를 때 | 힌트가 개월 수와 맞으면 힌트, 아니면 "검토 필요" | 틀린 힌트로 조용히 확정되는 것을 막는다 |

## 4. 데이터 모델

컬럼 추가만 한다. 테이블 신설·삭제·타입 변경은 없다.

### 4.1 `PaymentRecord` 추가 필드

| 필드 | 타입 | 뜻 |
| --- | --- | --- |
| `kind` | enum `PaymentRecordKind` = `FEE · JOINING_FEE · EVENT · OTHER · INTEREST` (기본 `FEE`) | 거래 분류. `FEE`만 회비 흐름(매칭·확정·납부 현황)에 들어간다 |
| `kindReason` | `String?` | 자동 분류 근거("거래구분 예금이자", "입금자명 '단체티'", "금액 100,000 = 가입비") 또는 재무가 바꾼 이유 |
| `nonFeeAmount` | `Int` (기본 0) | 회비가 아닌 부분. 125,000이면 100,000 |
| `nonFeeKind` | enum `NonFeeKind`? = `JOINING_FEE · EVENT · OTHER · OVERPAY` | 뗀 금액의 성격 |
| `monthHints` | `Json?` | `{ source: 'depositorName' \| 'memo', months: { year, month }[] }` |
| `needsReview` | `Boolean` (기본 false) | 자동 판정이 확신하지 못한 건. 일괄 확정 대상에서 제외 |
| `note` | `String?` | 재무의 처리 메모. 카카오뱅크 메모를 대체한다 |

- **회비로 계산하는 금액은 `amount - nonFeeAmount`다.**
  - 개월 수·부족/초과·확정 금액을 모두 이 값으로 계산한다.
  - `amount`는 통장 금액 그대로 둔다.
- **`status`는 지금 5개(PENDING·MATCHED·ERROR·CONFIRMED·SKIPPED) 그대로다.**
  - `kind ≠ FEE`인 건은 업로드 때 `SKIPPED`로 저장하고 `kindReason`이 사유가 된다.
  - 재무가 `kind`를 `FEE`로 바꾸면 매칭을 다시 돌려 `PENDING`/`MATCHED`로 복원한다(기존 unskip 흐름 재사용).
- **기존 275건은 기본값으로 남는다.**
  - `kind = FEE`, `nonFeeAmount = 0`, `needsReview = false`.
  - 이미 `SKIPPED`인 21건은 분류 규칙을 한 번 돌려 `kind`·`kindReason`만 채우는 보정 스크립트를 둔다(읽기 → 결과 제시 → 승인 후 실행).

### 4.2 `ClubMember` 추가 필드

### 4.3 `MembershipPayment` — 같은 달 추가 납부 허용

- `@@unique([clubMemberId, year, month])`를 일반 인덱스 `@@index([clubMemberId, year, month])`로 바꾼다.
  - 부족 납부 뒤 충당(20,000 → 5,000)을 같은 달에 두 번째 행으로 넣기 위해서다.
  - 중복 확정 방지는 `PaymentRecord.status` 가드(§5.7)가 맡는다.
- 연납은 `period = ANNUAL`로 12건 저장한다. 필드는 이미 있고 지금은 항상 `MONTHLY`다.

## 5. 자동 판정 파이프라인

```
파서 → ① 분류 → ② 매칭 → ③ 단가·개월 수 → ④ 월 배정 → 저장
                                         ↑
일괄 확정(버튼) → ③④를 다시 돌려 검증 → MembershipPayment 생성
단건 확정(시트) → 재무가 고친 회원·월·분할로 ③ 검증 → MembershipPayment 생성
```

모든 단계는 `src/lib/membership-fee/` 아래 순수 함수로 두고, API 핸들러는 조회·저장만 한다.

### 5.1 파서 (`excelParser.ts`)

- 출금은 지금처럼 제외한다.
- **거래구분을 보존한다.** `ParsedPaymentRow`에 `transactionType`을 추가한다.
- 거래일시는 지금처럼 `Date`로 파싱한다.

### 5.2 ① 분류 (`transactionClassifier.ts`, 신규)

입력: 파싱된 행, 단가 설정(일반·부부·가입비 금액, 연납 금액). 출력: `{ kind, kindReason, nonFeeAmount, nonFeeKind }`.

| 순서 | 규칙 | 결과 |
| --- | --- | --- |
| 1 | 거래구분이 `예금이자` | `INTEREST` |
| 2 | 입금자명에 행사 키워드(뒷풀이·뒤풀이·회식·월례회·단체티·단체복·티·콕·찬조·대회·참가비·등록비) | `EVENT`(콕·찬조·등록비는 `OTHER`) |
| 3 | 금액이 가입비(100,000)와 같고 입금자명에 월 힌트가 없음 | `JOINING_FEE` |
| 4 | 금액 − 가입비가 어떤 회비 단가(월·연납·부부)의 양의 배수 | `FEE`, `nonFeeAmount = 가입비`, `nonFeeKind = JOINING_FEE` |
| 5 | 금액이 회비 단가의 배수(연납 금액 포함) | `FEE` |
| 6 | 금액이 1개월 단가 미만 | `FEE`, `needsReview`(부족 입금 후보. 매칭이 되면 재무가 판단) |
| 7 | 그 외(배수가 아님) | `FEE`, `needsReview`, `kindReason = "금액이 단가 배수가 아님"`. 콕 합산 등은 재무가 분할한다 |

- **같은 금액 집중 규칙(배치 단위 후처리)**: 단가 배수가 아니고 가입비도 아닌 같은 금액이 7일 안에 5건 이상이면 그 건들을 `EVENT`로 본다(`kindReason` "같은 금액 N건 집중"). 키워드 없이 "이름 + 15,000"으로 들어오는 뒷풀이·단체티가 파일의 100건 이상이었다. 부족 납부는 이렇게 몰리지 않는다.
- 규칙 2의 키워드는 상수로 두고 테스트로 고정한다.
- 거래 연도의 단가가 없으면 **직전 연도 단가로 대체**하고 업로드 요약에 "YYYY년 단가로 판정했습니다"를 싣는다. 1월 파일이 연도 설정 전이라 막히는 일을 없앤다.
- 규칙 3에서 "박다람 100,000 (6~9월)"처럼 월 힌트가 있으면 회비 4개월로 본다. 메모가 없어지면 입금자명 힌트만 남으므로, 힌트 없는 100,000은 가입비로 두되 재무가 분류 한 번으로 회비로 바꿀 수 있다.
- 분류 결과는 재무가 상세 시트에서 언제든 바꿀 수 있다. 바꾸면 `kindReason`에 "수동 변경"과 이전 값을 남긴다.

### 5.3 ② 매칭 (`memberMatcher.ts` 수정 + `nameNormalizer.ts` 신규)

- **후보를 거래일 기준 활동 회원으로 좁힌다.**
  - 조건은 `matchable-members.ts`와 같다: `status ∈ {APPROVED, LEFT}`, `leftAt`이 없거나 거래일 이후, `feeObligationStartAt`이 없거나 거래일 이전.
  - 이 조건을 `src/lib/membership-fee/matchableMembers.ts` 함수로 빼서 API와 업로드가 같이 쓴다.
- **입금자명에서 이름 토큰을 뽑는다.**
  - 숫자·"월"·"회비"·"월회비"·"가입비"·"연회비"·구두점·공백을 떼고 남은 한글만 토큰으로 쓴다. 예: "최라옴3월회비" → "최라옴", "26.3월정마루" → "정마루", "김가온이나래5월" → "김가온이나래".
  - 지금의 7단계는 이 토큰으로 돌린다. 원문 기준 부분 일치도 유지해 둘 중 더 높은 confidence를 쓴다.
  - 유사도(7단계)는 토큰 길이가 2~3자일 때만 허용한다.
- **배우자 자동 추가는 지금처럼** 거래일 의무 기준으로 한다.
- 매칭 결과에 `confidence`가 **0.8 미만**이면 `needsReview`를 켠다. 정확(1.0)·부부(0.95)·부분 일치(0.85·0.8)는 통과하고 유사도(0.7)만 검토가 된다. 0.9로 두면 파일의 38%(부분 일치 247건)가 검토 대상이 돼 일괄 확정이 무력화된다.
- 매칭된 회원이 그 해 `FeeExemption`이면 `needsReview` "면제 회원입니다 — 회원을 바꿔주세요". 재무가 대신 입금한 건(입금자명 = 재무)이 면제 회원에게 확정되는 것을 막는다.

### 5.4 ③ 단가·개월 수 (`feeAmountResolver.ts`, 신규 — `coupleRateResolver.ts`를 흡수)

입력: 회원 ID 목록, 거래일, 회비 금액(`amount − nonFeeAmount`), 부부 이력·그룹, 의무 정보, 단가 설정. 출력: `{ perMemberPerMonth: number[], totalPerMonth, monthCount, period: 'MONTHLY' | 'ANNUAL', shortfall: boolean, overpay: number }`.

| 규칙 | 내용 |
| --- | --- |
| 부부 세대 단가 | 거래일 시점 부부(이력 → 그룹)이고 **두 사람 모두 매칭되고 모두 거래일 의무**일 때, 또는 운영자가 두 명을 명시 매칭했을 때(D안)만 세대 단가 |
| 개인 단가 | 그 외는 모두 개인 단가. 부부 중 한 명이 단독 입금하면 개인 단가로 본다(사용성 검토 P0 #2·#3 종료) |
| 연납 | 회비 금액이 그 유형의 ANNUAL 금액(또는 인원 수 배수)과 같으면 12개월, `period = ANNUAL`, 월 금액은 `annual / 12`(나머지는 앞 달부터 1원씩) |
| 월납 | 회비 금액 ÷ `totalPerMonth`가 정수면 그 개월 수 |
| 부족 | 회비 금액 < `totalPerMonth`이면 `shortfall`. 일괄 확정 제외, 단건에서 균등 배분 확정(지금과 같음) |
| 초과 | 배수가 아니고 1개월 이상이면 `overpay = 나머지`. `needsReview`. 재무가 `nonFeeAmount`로 떼거나 월을 고른다 |

- **업로드·단건 확정·일괄 확정이 이 함수만 쓴다.** `upload.ts`의 `validateAmount`/`detectMemberType` 사용, `confirm.ts`의 자체 부부 판정, `bulk-confirm.ts`의 `resolveMonthlyAmount` 호출을 모두 이 함수로 바꾼다.
- `amountValidator.ts`의 하위 호환 함수(`validateAmount`, `detectMemberType`)는 호출처가 없어지면 삭제한다.

### 5.5 ④ 월 배정 (`monthAssigner.ts`, 신규 — `monthSuggester.ts`·`attachLastPaidYearMonth.ts` 위에 얹음)

- **월 힌트 파서** (`monthHintParser.ts`, 신규): 입금자명(과거 파일은 메모도)에서 `{ year, month }[]`를 뽑는다.
  - 지원 형태: "3월", "1,2월", "1/2월", "1월2월", "6~9월", "6-9월", "12월1월"(연도 경계), "26.3월", "45월"(4·5월, 두 자리는 각 자리로), "3,4,5월회비".
  - 연도는 거래일 기준으로 정한다. 거래월보다 3개월 이상 뒤면 전년, 그 외는 당해. 12월→1월 같은 경계는 연속으로 본다.
- **배정 규칙**
  - 힌트가 있고 개수가 ③의 `monthCount`와 같으면 힌트를 쓴다.
  - 힌트가 없으면 지금의 `suggestMonths`(밀린 달 우선, 의무 월만, 납부된 달 제외)를 쓴다.
  - 힌트 개수가 다르거나 힌트 월이 의무 월이 아니거나 이미 납부된 달이면 `needsReview`를 켜고 힌트와 제안을 둘 다 시트에 보여 준다.
- 결과는 `suggestedSelections: { year, month }[]`로 레코드에 붙여 내려보낸다(지금의 `nextSuggestedYearMonth`를 일반화).
- **검토 필요·사유·배정 월은 조회할 때마다 다시 계산한다.** 업로드 때 저장한 `needsReview`는 스냅샷이고, 화면과 일괄 확정은 조회 시점의 계산을 쓴다. 재무가 휴회·시작월을 고치면 그 건은 손대지 않아도 일괄 확정 대상이 된다.
- 힌트 월이 의무 시작 전이면 시트에 **"의무 시작월을 N월로 앞당기기"** 를 둔다. 누르면 `feeObligationStartAt`을 그 달 1일로 바꾸고 다시 판정한다. 이미지 대조에서 10명이 이 유형이었다.

### 5.6 저장 규칙 (`upload.ts`)

| 분류·판정 | 저장 상태 |
| --- | --- |
| `kind ≠ FEE` | `SKIPPED`, `kindReason` |
| `FEE`, 매칭 실패 | `PENDING` |
| `FEE`, 매칭 성공, 개월 수 확정 | `MATCHED` |
| `FEE`, 매칭 성공, 부족/초과/힌트 불일치/낮은 confidence | `MATCHED` + `needsReview` |
| `FEE`, 단가 설정 없음 등 처리 불가 | `ERROR` |

- **중복 감지**: 같은 클럽에 같은 거래일시·금액·입금자명인 레코드가 있으면 새 배치에 넣지 않고 응답의 `duplicates` 목록에 담아 "이미 올라온 N건은 제외했습니다"로 알린다.
  - 5~10월 파일을 올릴 때 1~4월 배치와 겹치는 224건을 걸러낸다.
- 업로드 응답 요약에 분류별 건수와 `needsReview` 건수를 넣는다.

### 5.7 확정

- **일괄 확정(`bulk-confirm.ts`)**
  - 대상: `status = MATCHED`, `kind = FEE`, `needsReview = false`, 매칭 회원 있음.
  - 레코드마다 ③·④를 다시 돌려 그 결과로만 확정한다(업로드 시점과 DB가 달라졌을 수 있다).
  - `paymentRecord.updateMany({ where: { id, status: 'MATCHED' } })`로 가드하고 0건이면 "이미 처리됨"으로 실패에 넣는다(사용성 검토 P0 #1 종료).
  - 제외된 건은 응답에 사유와 함께 돌려줘 화면이 "제외 N건(사유 보기)"로 보여 준다.
- **단건 확정(`confirm.ts`)**
  - 입력에 `kind`·`nonFeeAmount`·`nonFeeKind`·`note`를 받는다.
  - 선택한 월이 의무 월인지 검증(지금과 같음), 금액은 ③으로 검증한다.
  - 부족 확정은 지금처럼 균등 배분, 초과는 미할당. 미할당이 남으면 `nonFeeKind = OVERPAY`, `nonFeeAmount`에 기록해 흔적을 남긴다.
  - **부족분 충당**: 고른 달에 이미 납부가 있어도 "기존 납부 합계 + 이번 회비 금액 ≤ 그 달 단가"면 허용한다(두 번째 행). 시트는 부족 납부가 있는 달에 "N월 부족분 충당" 칩을 보여 준다.

### 5.8 납부월 이월

- **휴회·탈퇴로 의무가 없어진 달에 납부가 있으면 다음 의무월로 옮긴다.**
  - 사례: 4월 회비를 낸 뒤 4월 휴회를 등록("4월병가, 5월로 이월"), 연납 뒤 중간 휴회.
  - 휴회 저장 API가 범위 안 납부 건수를 응답에 싣고, 회원 상세가 "휴회 기간에 납부 N건이 있습니다 — 다음 의무월로 이월" 을 보여 준다.
  - `POST /api/clubs/[id]/membership-fee/payments/shift` `{ paymentIds }` — 각 납부를 그 회원의 다음 미납 의무월로 옮긴다(`year`·`month`만 바뀜, `paymentRecordId`는 유지). 옮길 달이 없으면 그 건은 실패 목록에.
  - 대시보드 격자에서도 휴회 칸에 납부가 겹쳐 있으면 칸 `title`에 "납부 있음 — 이월 필요"를 붙인다.

### 5.9 선택 항목 분류 변경

- 처리 화면의 검토 필요·대기·매칭됨 탭에서 여러 건을 골라 **분류를 한 번에 바꾼다** (`POST records/bulk-set-kind` `{ recordIds, kind }`).
- `FEE`가 아닌 분류로 바꾸면 `SKIPPED`, `FEE`로 바꾸면 §5.6의 저장 규칙으로 재판정. 응답은 일괄 패턴(`results.success/failed`).
- 같은 금액 집중 규칙이 놓친 행사 건을 재무가 금액 필터로 모아 한 번에 처리하는 용도다.

### 6.2 내보내기 API (`GET /api/clubs/[id]/membership-fee/export?year=`)

- **대시보드와 같은 계산을 쓴다.**
  - `dashboard.ts` 안의 회원별 상태 계산을 `src/lib/membership-fee/memberYearStatus.ts`의 `buildMemberYearStatus()`로 뺀다.
  - 대시보드 API와 내보내기 API가 이 함수를 같이 쓴다. 두 결과가 다를 수 없다.
- **표 모양은 재무의 기존 엑셀(첨부 이미지)과 같다.**
  - 제목 "YYYY년 월회비 납부현황", 오른쪽 위 "반영일 : YYYY.M.D"(내보낸 날), 범례 5칸(완납·미납·면제·병가·해당없음).

  - 행 순서: `position`이 있는 회원을 `positionOrder` 순으로 먼저, 그 아래 굵은 선, 나머지는 가나다.
  - 그 해에 의무가 한 달이라도 있는 회원을 모두 넣는다. 탈퇴한 회원은 탈퇴 다음 달부터 "해당없음".
- **칸 규칙**

| 상태 | 조건 | 색 |
| --- | --- | --- |
| 완납 | 의무 월이고 납부 있음 | 베이지 |
| 미납 | 의무 월이고 납부 없음, 지난 달 또는 이번 달 | 빨강 |
| 아직 안 온 달 | 의무 월이고 납부 없음, 다음 달 이후 | 흰색 |
| 면제 | 그 해 `FeeExemption` | 파랑 |
| 병가 | `MemberLeave`에 포함. `reason`이 있으면 칸에 글자 | 초록 |
| 해당없음 | 의무 시작 전, 탈퇴 후 | 회색 |

- 비고에는 `position`.
- **구현**: `xlsx` 패키지는 무료판에서 셀 색을 쓸 수 없다. `exceljs`를 추가해 서버에서 만들고 `Content-Disposition`으로 내려준다. 파일명 `회비납부현황_{year}_{YYYYMMDD}.xlsx`.
- 권한은 다른 회비 API와 같이 `Role.ADMIN`.

## 10. 열린 질문

- 내보내기에서 **탈퇴 회원을 넣을지**. 기본은 "그 해 의무가 한 달이라도 있으면 포함". 재무의 기존 엑셀에는 탈퇴자가 없어 보여 확인이 필요하다.
- 행사 키워드 목록의 초기값. §5.2의 목록은 2026년 파일에서 뽑았다. 운영하며 늘린다.
