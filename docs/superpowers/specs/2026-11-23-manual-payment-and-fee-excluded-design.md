# 회비 정산 — 납부 직접 추가와 회비 대상 아님 설계

작성일: 2026-11-23
브랜치: `feat/membership-fee-settlement`
상태: 설계 승인 (2026-11-23, 대화에서 "설계 대로 해 줘")

## 1. 배경

- **목표는 앱만으로 재무의 "2026년 월회비 납부현황" 표를 그대로 따라 하는 것이다.**
  - 재무 표(11/4 반영)와 앱을 대조해 차이를 하나씩 없애 왔다. DB를 직접 고쳐 기능 공백을 가리지 않는다.
- **남은 차이 가운데 두 가지는 지금 앱으로 나타낼 방법이 없다.**
  - 통장에 입금이 없지만 재무 표는 완납인 달.
    - 회원 A 2026-09: 회비를 실수로 콕 계좌로 보냈다. 회비 통장으로 옮길 계획은 없고, 낸 것으로 채우기만 한다.
    - 회원 B 2026-10·11: 재무 표는 완납인데 통장 입금이 없다. 재무님께 까닭을 묻는 중이다.
  - 재무 표에 아예 없는 코치.
    - 코치 C(2026-08 가입)은 지금 앱에서 8–11월이 미납이다.
    - 코치 D는 2026년 면제(사유 "코치님")라 내보낸 엑셀에 재무 표에 없는 파란 면제 줄이 생긴다.
    - 재무 표는 명예회원을 면제 줄로 싣고, 코치는 싣지 않는다. 그래서 코치는 면제가 아니라 회비 대상이 아닌 사람이다.

## 2. 목표 · 비목표 · 실패로 볼 것

| 구분 | 내용 |
| --- | --- |
| 목표 | 회원 상세에서 "납부 직접 추가"로 달·금액·사유를 넣으면 납부 현황·엑셀·월별 납부율에서 완납이 된다 |
| 목표 | 회원 상세에서 "회비 대상 아님"을 켜면 납부 현황·엑셀·미납자 목록·대시보드 회원 수에서 빠진다 |
| 비목표 | 다른 계좌로 간 돈을 회비 통장으로 옮기는 회계 처리 |
| 비목표 | 직접 추가한 납부의 수정 (지우고 다시 넣는다) |
| 비목표 | 회비 대상 아님을 기간 단위로 두기 |
| 실패로 볼 것 | 직접 추가한 금액이 대시보드 "총 수입"에 섞여 통장 잔액과 어긋남 |
| 실패로 볼 것 | 직접 추가가 입금 내역 목록·최근 업로드·최신 거래일·업로드 중복 검사에 나타남 |
| 실패로 볼 것 | 같은 달에 납부가 두 번 잡히거나, 의무가 없는 달에 납부가 생겨 이월 경고가 뜸 |

## 3. 접근

### 3.1 직접 추가한 납부를 어디에 저장하나

| 방법 | 내용 | 판단 |
| --- | --- | --- |
| **A. 납부 기록의 입금 칸을 비울 수 있게 (선택)** | `MembershipPayment.paymentRecordId`를 nullable로, `manualReason`을 더한다 | 납부를 읽는 곳(현황·내보내기·미납·확정 계획·이월)이 그대로 완납으로 본다. 입금 쪽 화면에는 나타나지 않는다 |
| B. 가짜 입금 기록(`PaymentRecord`)을 만든다 | 스키마를 바꾸지 않는다 | 버림. `PaymentRecord`는 업로드 배치가 꼭 있어야 하고, 입금 내역 목록·최근 업로드·최신 거래일·업로드 중복 검사에 섞인다 |
| C. 별도 테이블 | `ManualPayment` 같은 새 테이블 | 버림. 납부를 읽는 곳마다 두 테이블을 합치도록 고쳐야 한다 |

- 2026-11-22 기준 납부 기록 781건은 모두 입금에 묶여 있다.
- 운영(main)에는 회비 화면·API가 없어, 칸을 nullable로 바꿔도 운영이 깨지지 않는다.

### 3.2 회비 대상 아님을 어떻게 나타내나

| 방법 | 판단 |
| --- | --- |
| **A. `ClubMember`에 칸 하나 (선택)** | 모든 해에 걸린다(직책과 같다). 지금 두 사람 모두 처음부터 코치다 |
| B. 면제 사유 "코치"로 처리 | 버림. 재무 표에 없는 면제 줄이 생긴다 |
| C. 기간 단위 | 버림. 지금 필요한 경우가 없다 |

- 대가: 켠 회원은 지난해 표에서도 빠진다.

## 4. 설계

### 4.1 DB (마이그레이션 하나)

| 테이블 | 바꿀 것 |
| --- | --- |
| `MembershipPayment` | `paymentRecordId` → NULL 허용. 관계 `paymentRecord`도 선택으로 |
| `MembershipPayment` | `manualReason TEXT NULL` 추가. 직접 추가한 납부의 사유 |
| `ClubMember` | `feeExcluded BOOLEAN NOT NULL DEFAULT false` 추가 |

- **직접 추가한 납부 = `paymentRecordId`가 없는 납부다.**
  - 이때 `manualReason`은 늘 있다. 이 규칙은 API가 지킨다.
  - DB CHECK 제약은 두지 않는다. Prisma 스키마로 나타낼 수 없어 `migrate diff`의 드리프트 확인과 어긋난다.
- 적용은 CLAUDE.md의 순서를 따른다: `migrate diff`로 SQL을 만들고, 사용자에게 보여 승인을 받은 뒤 적용한다.

### 4.2 납부 직접 추가 API

| 메서드 · 경로 | 하는 일 |
| --- | --- |
| `GET /api/clubs/[id]/members/[userId]/manual-payments` | 그 회원의 직접 추가한 납부 목록 (연·월·금액·사유·넣은 날·넣은 사람) |
| `GET /api/clubs/[id]/members/[userId]/manual-payments/suggest?year=&month=` | 그 달의 기본 금액. 그 달에 부부였으면 부부 단가, 아니면 일반 단가 (그 해 월 단가) |
| `POST /api/clubs/[id]/members/[userId]/manual-payments` | `{ year, month, amount, reason }`로 한 달을 넣는다 |
| `DELETE /api/clubs/[id]/members/[userId]/manual-payments/[paymentId]` | 직접 추가한 납부만 지운다. 입금에 묶인 납부는 거절 |

- 모두 관리자 전용이고, `.claude/rules/api-handler-conventions.md`를 따른다.
- **넣기 전에 막는 경우 (400)**

| 경우 | 문구(안) |
| --- | --- |
| 이미 그 달에 납부가 있음 (입금이든 직접 추가든) | 이미 납부가 있는 달입니다 |
| 의무가 없는 달 (가입 전·휴회·탈퇴 후) | 회비 의무가 없는 달입니다 |
| 면제 기간의 달 | 면제 기간인 달입니다 |
| 금액이 1원 미만이거나 정수가 아님 | 금액을 확인해주세요 |
| 사유가 비었음 | 사유를 입력해주세요 |

- 사유는 "다른 계좌로 보냄", "현금으로 받음", 기타(직접 쓴 글, 100자까지) 가운데 하나다. 저장은 고른 글자 그대로, 기타면 쓴 글자를 `manualReason`에 둔다.
- 같은 회원의 확정과 겹치지 않게, 입금 확정(`applyPlan`)처럼 트랜잭션 안에서 회원 행을 잠그고 "이미 납부" 검사를 다시 한다.
- `period`는 `MONTHLY`, `confirmedById`는 넣은 관리자의 회원 id다.

### 4.3 회비 대상 아님

- **회원 정보 저장 API(`PATCH …/members/[userId]/fee-obligation`)가 `feeExcluded`를 받는다.**
  - 보낸 칸만 고치는 지금 방식 그대로다.
- **빼는 곳**
  - `loadMemberYearData`의 회원 조회 → 대시보드 납부 현황·월별 납부율·회원 수, 내보내기가 함께 빠진다.
  - 대시보드의 면제 회원 수도 조회된 회원 안에서만 센다. 지금은 클럽 전체 면제를 센다.
  - 미납자 목록(`unpaid.ts`)의 회원 조회.
- 입금 매칭 후보, 부부 관리, 면제 등록 화면은 바꾸지 않는다.

### 4.4 대시보드 총 수입

- **"YYYY년 총 수입"과 월별 금액은 입금에 묶인 납부만 더한다.**
- 직접 추가한 납부가 있으면 총 수입 아래에 한 줄을 따로 보인다.
  - 문구(안): "직접 추가 2건 · 50,000원 (총 수입에 넣지 않음)"
- 납부 현황 칸과 월별 납부율은 직접 추가도 완납으로 센다(재무 표와 같다).

### 4.5 회원 상세 화면

```
회원 상세
 ├ 회비 설정
 │   ☐ 회비 대상 아님 (코치 등)
 │      켜면 납부 현황·엑셀·미납자 목록에서 빠집니다.
 ├ 휴회/병가 기간        [휴회 추가]
 └ 직접 추가한 납부
     2026.10 · 25,000원 · 재무 표 기준        ← 누르면 시트(내용 + 삭제)
     2026.09 · 25,000원 · 다른 계좌로 보냄
     [납부 직접 추가]  → 시트: 연월 · 금액 · 사유
```

- **회비 대상 아님은 체크하는 즉시 저장한다.**
  - 성공·실패를 토스트로 알린다.
- **직접 추가한 납부 목록은 최근 달부터 보인다.**
  - 목록 아래 설명(안): "통장 입금 없이 낸 것으로 칠 달입니다. 납부 현황에는 완납으로 보이고, 총 수입에는 넣지 않습니다."
- **[납부 직접 추가] 시트**
  - 연월을 고르면 `suggest`로 금액을 미리 채운다. 고칠 수 있다.
  - 사유는 면제 등록 시트(`ExemptionRegisterSheet`)처럼 라디오 세 개로 고르고, 기타면 글 칸이 나온다.
  - 실패하면 서버가 준 사유를 토스트로 보인다.
- **지우기**: 행을 누르면 시트가 열리고, [삭제]는 `useConfirm`으로 한 번 더 묻는다.
- 부품·토큰은 `docs/가이드/디자인-시스템.md`를 따른다. 회비 대상 아님 체크는 `MemberFeeDetailView`에, 직접 추가한 납부 목록과 시트는 새 부품 `ManualPaymentSection`에 둔다(`MemberFeeDetailView`가 이미 400줄이 넘는다). 둘 다 `/dev/admin-preview`에 가짜 데이터로 올려 본다.

### 4.6 그 밖에 따라오는 것 (바꾸지 않아도 맞게 돈다)

| 곳 | 직접 추가한 납부에 대해 |
| --- | --- |
| 입금 확정 계획(`confirmPlanner`) | 기존 납부를 모두 읽으므로, 뒤에 온 입금은 그 달을 건너뛴다 |
| 휴회 등록·이월(`findOrphanPayments`, `payments/shift`) | 납부 행 단위라 똑같이 다룬다 |
| 확정 취소·업로드 배치 삭제 | 입금에 묶인 납부만 지우므로 건드리지 않는다 |
| 입금 내역 목록·최근 업로드·최신 거래일·업로드 중복 검사 | `PaymentRecord`만 보므로 나타나지 않는다 |

- 타입 `MembershipPayment`(`src/types/membership-fee.types.ts`)의 `paymentRecordId`는 `string | null`이 되고 `manualReason`이 더해진다. `tsc`가 null을 다루지 않는 곳을 찾아 준다.

## 5. 검증

- **단위·API·화면 테스트** (TDD)
  - 넣기 검사(이미 납부·의무 없음·면제·금액·사유), 기본 금액(부부·일반).
  - 로더: 회비 대상 아님 제외, 총 수입에서 직접 추가 제외, 직접 추가 건수·금액.
  - API: 권한, 막는 경우, 입금에 묶인 납부 삭제 거절.
  - 화면: 목록·시트·체크, 대시보드의 따로 보이는 줄.
- **실제 데이터** (마이그레이션 적용 뒤, 화면 또는 같은 API로)
  - 회원 A 2026-09 25,000원 "다른 계좌로 보냄", 회원 B 2026-10·11 각 25,000원 (재무님 답이 없으면 기타 "재무 표 기준").
  - 코치 C·코치 D 회비 대상 아님 켜기. 코치 D의 2026 면제(id 6)를 지울지는 그때 사용자에게 묻는다.
  - 내보낸 엑셀에서 세 칸이 완납이고 두 코치 줄이 없는지, 대시보드 총 수입이 그대로인지 본다.

## 7. 내가 정한 것 (빌더 판단)

- 기본 금액을 위한 `suggest` API를 따로 둔다. 목록 API에 단가표를 싣는 것보다 화면이 단순하다.
- DB CHECK 제약 대신 API에서 규칙을 지킨다.
- 회비 대상 아님은 체크 즉시 저장한다. 회비 설정의 [저장] 버튼은 시작월·탈퇴일 전용으로 둔다.
- 문구는 모두 "(안)"이다. 만들 때 바꾸면 보고한다.
