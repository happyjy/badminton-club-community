# 코드 리뷰 — 대회 신청 시스템 (`feat/tournament-entry-impl`)

- **대상:** `feat/tournament-entry-impl` vs `main` (약 13.9k 라인) + 워킹 트리 변경
- **작성일:** 2026-08-16
- **선행 확인:** 타입체크는 기존 `sms-notification.test.ts` 오류를 제외하면 정상, 신규 테스트 15개 스위트 통과

## 요약

| 심각도   | 건수 | 성격                                              |
| -------- | ---- | ------------------------------------------------- |
| Critical | 2    | 배포 시 스키마 불일치, 타 클럽 데이터 변조        |

즉시 처리 대상은 **Prisma 마이그레이션 누락**과 **PATCH 테넌시 미검증** 두 건입니다.

## Critical

### 1. Prisma 마이그레이션 누락 — `prisma/build-schema.ts:14,22`

`memberLeave.prisma`, `membershipFee.prisma` 가 생성 스키마에 추가되어 **13개 모델 + 2개 enum** 이 늘었지만, 이에 대응하는 **마이그레이션이 하나도 없습니다.**

```bash
grep -rl "FeeType\|MemberLeave" prisma/migrations/   # 결과 없음
```

두 파일 모두 `main` 에 존재하지 않습니다.

- 배포 시 `prisma migrate deploy` 는 대회 테이블만 만들고 이 테이블들은 만들지 않음
- 생성된 클라이언트는 `prisma.feeType` 등을 노출하지만 실제 테이블이 없어 런타임 실패
- `prisma migrate status` 가 드리프트를 보고

대회 기능과 무관한 파일이라 **다른 브랜치에서 넘어온 머지 아티팩트**로 보입니다. 의도한 변경인지 먼저 확인이 필요합니다.

### 2. 종목 수정 시 테넌시 미검증 — `src/pages/api/clubs/[id]/tournaments/[tournamentId]/index.ts:167`

PATCH 루프가 클라이언트가 보낸 id 를 그대로 사용합니다.

```ts
// 현재: tournamentId 바인딩 없음
tournamentEventType.update({ where: { id: eventType.id } });
```

- A 클럽 관리자가 B 클럽 대회의 종목 id 를 넘겨 이름·참가비·인원수를 임의로 수정 가능
- 더 심각한 부작용: 넘긴 id 가 `existing.eventTypes` 에 없으므로, 관리자 **본인 클럽의 모든 종목**이 `:146` 의 "삭제됨" 분기로 빠져 삭제 또는 비활성화됨

**수정 방향:** `updateMany({ where: { id, tournamentId } })` 로 대회에 바인딩.

## High

### 3. 취소 이력 유실 — `entries/[entryId]/index.ts:88`

```ts
entryPlayer.deleteMany({ where: { entryId } }); // 전체 선수 삭제
// :90 — CANCELED entryEvent 는 의도적으로 보존
```

`EntryEventPlayer` 가 `entryPlayer` 삭제에 cascade 되므로, 보존한 `CANCELED` 이벤트의 선수 연결이 함께 끊깁니다. 결과적으로

- 신청 내역 수정 이후 취소된 행이 선수 없이 렌더링됨
- `toCsvRows` 가 `eventPlayers` 를 순회하므로 CSV 내보내기에서 누락
- 코드가 명시적으로 지키려던 취소 감사 기록이 파괴됨

### 4. 게스트 게시글 삭제의 클럽 스코프 누락 — `src/pages/api/clubs/[id]/guests/[guestId]/index.ts:25`

`guestPost` 를 `guestId` 만으로 조회하는데, 신규 DELETE 분기는 URL 의 `clubId` 로 권한을 검사합니다. 아무 클럽의 관리자나 경로에 자기 클럽 id 를 넣어 **타 클럽 게시글을 삭제**할 수 있습니다.

> 별도 확인 필요: 이 변경으로 작성자 본인 삭제 기능이 완전히 제거되었습니다(API·UI 버튼 모두 `isAdmin` 분기 안으로 이동). 의도한 정책인지 확인이 필요합니다.

### 5. `router.isReady` 미체크로 인한 잘못된 빈 상태 — `my.tsx:44`

신규 페이지 6개 모두 `router.isReady` 를 확인하지 않고, `getServerSideProps` 도 없습니다.

하드 리프레시 시 `router.query` 가 `{}` → 훅이 `enabled: false` → react-query v5 에서 `isLoading = isPending && isFetching` 이 **false** 이고 `data` 는 `undefined`. 즉 `isLoading` 가드를 그냥 지나칩니다.

- 이미 신청한 사용자에게 "아직 신청 내역이 없습니다" + 신청하러 가기 버튼이 표시됨
- 중복 제출을 유도하는 잘못된 화면

### 6. 대회 삭제 경고문이 거짓 — `admin.tsx:114`

같은 원인. 대시보드가 신청 0건으로 그려지고, `DeleteTournamentDialog` 가 `entryCount={entries?.length ?? 0}` (`:155`) 을 받습니다. 이 구간에 삭제하는 관리자는 **N건의 신청이 함께 지워진다는 안내를 전혀 보지 못합니다.** 이름을 타이핑해 확인시키는 UX 의 근거가 되는 문구가 조용히 틀립니다.

### 7. 폼 입력 유실 — `apply.tsx:49`

reset effect 가 `myEntry` **객체 아이덴티티**에 의존해 `methods.reset(...)` 을 호출합니다. refetch 마다 아이덴티티가 바뀌므로,

- 페이지를 벗어났다 돌아오거나
- 폼이 열린 상태에서 `invalidateQueries(['myEntry'])` 가 발생하면

입력하던 내용이 조용히 사라집니다. **수정 방향:** `myEntry.id` 변화로 게이트하거나 `hasResetRef` 사용.

### 8. 종목 Select 에 required 규칙 없음 — `EventListField.tsx:95`

종목 `<Select>` 가 `value`/`onChange` 로만 제어되고 `register` 를 거치지 않아 `events.${index}.eventTypeId` 에 `required` 규칙이 없습니다. 빈 "선택해주세요" 상태로 `handleSubmit` 이 통과해 `eventTypeId: ''` 이 전송되고, 인라인 에러 대신 **서버 400** 을 받습니다.

## Medium

### 9. 검증 실패가 화면에 표시되지 않음 — `EventListField.tsx:105,113,123`

`register` 에 `required: true` 를 걸었지만 해당 `FormField`(`:102`, `:110`, `:120`)에 신규 `error` prop 을 넘기지 않고, `apply.tsx` 에도 에러 요약이 없습니다. 연령을 선택하지 않으면 `handleSubmit` 이 막히는데 화면에는 아무것도 뜨지 않아 **제출 버튼이 고장난 것처럼 보입니다.**

`EntrySummary.tsx:55,69`, `TournamentForm.tsx:77,116` 도 동일합니다.

> 직전 커밋(`adf9f1a`)에서 `PlayerListField` 에 대해 고친 것과 정확히 같은 문제가 이 파일들에 남아 있습니다.

### 10. 자동 채움이 사용자 입력을 덮어씀 — `apply.tsx:83`

autofill effect 가 `players.0.*` 와 `depositorName` 을 무조건 `setValue` 합니다. `myEntry` 는 로딩 중 `undefined` → 쿼리 확정 후 `null` (`my` API 가 `entry: null` 반환) 로 바뀌므로, **사용자가 이미 타이핑한 뒤에 다시 실행**되어 입력을 덮어씁니다. run-once 가드가 필요합니다.

### 11. 선수 삭제 가드 누락 — `PlayerListField.tsx:69`

`assignedKeys` 를 렌더링된 이벤트 슬롯에서 파생하는데, `EventListField` 는 `playerCount === 0` 이면 렌더링을 건너뜁니다. 렌더 슬롯 밖에서 보유 중인 키는 삭제 버튼을 비활성화하지 못합니다. 여전히 참조 중인 선수를 삭제하면 서버에서 "종목에 배정된 선수를 찾을 수 없습니다" 로 실패하고, 필드 단위 표시는 없습니다.

**수정 방향:** 비활성화에만 의존하지 말고 remove 핸들러에서 `playerKeys` 를 정리.

### 12. `isCustom` 이 되돌아오지 않음 — `PresetOrCustomInput.tsx:30`

effect 가 `isCustom` 을 `true` 로만 래치하고 `false` 로 되돌리지 않습니다. 상태가 `field.id` 를 따라 이동하므로, `EventTypeEditor` 의 `remove(index)`(`:93`) 이후 살아남은 행에서 **프리셋 값이 자유 입력창 안에 렌더링**될 수 있습니다.

## Low

### 13. 내 신청 조회의 클럽 스코프 누락 — `entries/my.ts:32`

`tournamentId_userId` 에 대한 `findUnique` 가 `clubId` 로 스코프되지 않아, A 클럽 회원이 A 클럽 URL 로 B 클럽 대회의 자기 신청을 읽을 수 있습니다. 본인 데이터에 한정되어 영향은 제한적이나, 형제 라우트들이 모두 `tournament: { clubId }` 로 강제하는 테넌시 검사를 깨뜨립니다.

### 14. 참가비 합계 경합 — `events/[entryEventId].ts:65`

`resolveEntryStateAfterCancel` 가 **트랜잭션 밖**에서 읽은 행으로 `totalFee` 를 계산한 뒤 트랜잭션 안에서 씁니다. 같은 신청의 서로 다른 종목을 동시에 취소하면 둘 다 취소 이전 집합을 기준으로 계산해 `totalFee` 가 한 종목 참가비만큼 과다 계상됩니다.

**수정 방향:** 생성 경로(`entries/index.ts:99`)가 이미 올바르게 하듯 `$transaction` 안에서 재조회.
