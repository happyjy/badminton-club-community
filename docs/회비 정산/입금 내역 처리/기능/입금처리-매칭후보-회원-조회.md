# 입금 처리 매칭 후보 회원 조회 기준

## 1. 배경 (Why)

회비 입금 내역 처리(`/clubs/[id]/membership-fee/process`, `/upload`) 화면의 매칭 회원 드롭다운(`MemberMultiSelectDropdown`)은 다음 두 곳에서 사용된다.

- **필터** (`PaymentRecordFilters`) — "선택한 회원이 포함된 입금 건만 보기"
- **행별 매칭 수정** (`PaymentRecordTable`) — 매칭 실패/오매칭 건의 회원을 직접 지정

기존에는 `/api/clubs/members?clubId=...` 를 호출해 **클럽의 모든 ClubMember**(status 무관)를 받아 표시했다.

문제:

1. **PENDING/REJECTED 회원도 후보에 노출** — 가입 대기/거절된 사람이 매칭 가능 회원처럼 보임
2. **운영 순서 의존성** — 회원이 LEFT 처리된 뒤 과거 거래분을 처리하려 하면, 그 회원이 후보에서 사라짐. 운영자가 "LEFT 처리 전에 입금 처리"를 매번 신경 써야 함
3. **회원 누적 시 페이로드 증가** — 클럽이 오래 운영되어 누적 회원이 1,000명에 가까워지면 매번 전체 회원 목록을 받게 됨

핵심 통찰: **표시 기준은 "현재 상태"가 아니라 "거래일 시점의 상태"여야 한다.** 6월 거래분을 8월에 처리하더라도 6월에 활동 중이던 회원은 후보에 떠야 한다.

---

## 2. 목표

1. 입금 처리 화면의 매칭 후보를 **거래일 시점에 활동 중이던 회원**으로 한정한다.
2. 운영자가 "탈퇴 처리 전 입금 처리"를 의식하지 않아도 정상 매칭이 가능하다.
3. 누적 회원수가 1,000명 이상으로 늘어도 응답이 자동으로 조회 범위 시점의 활동자로 좁혀진다.
4. 후보로 노출된 LEFT 회원은 시각적으로 구분해서 매칭 시 혼동을 줄인다.

---

## 3. 매칭 후보 회원 정의

거래일 범위 `[from, to]`가 주어졌을 때, 매칭 후보는 다음 조건을 모두 만족하는 `ClubMember`:

- `clubId` 일치
- `status` ∈ {`APPROVED`, `LEFT`} — `PENDING`/`REJECTED`는 제외
- `leftAt`이 NULL **또는** `leftAt >= from` — 거래일 범위 시작 이후에 탈퇴했거나 아직 활동 중
- `feeObligationStartAt`이 NULL **또는** `feeObligationStartAt <= to` — 회비 의무 시작 전 매칭 방지

> 거래일 범위가 주어지지 않을 때(예: 업로드 직후 records가 비어있는 경우)는 `status` 필터만 적용. `leftAt`/`feeObligationStartAt` 조건은 생략한다.

---

## 4. 거래일 범위 결정 방식

화면별로 매칭 후보 조회 범위 `[from, to]`를 다음과 같이 결정한다.

| 화면                            | 범위 출처                                       |
| ------------------------------- | ----------------------------------------------- |
| `process.tsx` — 범위 모드       | `appliedRange` (사용자가 적용한 거래일 from/to) |
| `process.tsx` — batch 진입 모드 | 해당 batch records의 `transactionDate` min/max  |
| `upload.tsx`                    | 막 업로드된 records의 `transactionDate` min/max |

이렇게 하면 한 화면에서 보고 있는 모든 입금 건이 같은 후보군을 공유한다. 한 번에 보는 범위가 보통 1~3개월이므로, 누적 회원이 많아도 응답은 그 시점의 활동자로 자연스럽게 한정된다.

## 5. API

### 5.1 신규 엔드포인트

`GET /api/clubs/[id]/membership-fee/matchable-members?from=<ISO>&to=<ISO>`

- **인증**: `withAuth` + 해당 클럽 ADMIN
- **응답**:
  ```json
  {
    "data": {
      "members": [
        { "id": 1, "name": "홍길동", "status": "APPROVED", "leftAt": null },
        {
          "id": 2,
          "name": "김철수",
          "status": "LEFT",
          "leftAt": "2026-03-15T..."
        }
      ]
    },
    "status": 200,
    "message": "매칭 가능 회원을 불러왔습니다"
  }
  ```
- **정렬**: 한글 이름 가나다순
- **위치**: `src/pages/api/clubs/[id]/membership-fee/matchable-members.ts`

### 5.2 기존 `/api/clubs/members` 와의 관계

`/api/clubs/members`는 다른 화면(예: 회원 관리, SMS 수신자 선택)도 사용하는 범용 엔드포인트이므로 건드리지 않는다. 회비 정산 도메인 전용 의미를 URL에 담아 신규 엔드포인트로 분리했다.

> 참고: `/api/clubs/members`는 주석에 "승인된 멤버만 가져오기"로 적혀 있으나 실제로는 status 필터가 없다 (구현/주석 불일치). 별개 이슈로 남겨둔다.

## 6. 클라이언트

### 6.1 React Query 훅

`src/hooks/membership-fee/useMatchableMembers.ts`

```typescript
useMatchableMembers(clubId, { from, to });
// queryKey: ['matchableMembers', clubId, from, to]
```

- `from`/`to`가 모두 빈 값이면 status 필터만 적용된 응답을 받는다.
- 같은 화면에서 거래일 범위가 같은 모든 호출은 캐시 1회로 공유된다.

### 6.2 드롭다운 UI — LEFT 회원 표시

`src/components/molecules/membership-fee/MemberMultiSelectDropdown.tsx`의 `Member` 인터페이스에 `status?`, `leftAt?` 추가. LEFT 회원 표시 규칙:

| 위치               | 표시                                                               |
| ------------------ | ------------------------------------------------------------------ |
| 옵션 행 텍스트     | 회색 (`text-gray-500`)                                             |
| 옵션 행 우측 배지  | `탈퇴 YYYY-MM` (회색 박스)                                         |
| 선택된 칩          | 파란 톤 → 회색 톤 (`bg-gray-200 text-gray-700`) + `(탈퇴 YYYY-MM)` |
| 닫힌 드롭다운 라벨 | `홍길동 (탈퇴 2026-03)` 식으로 표기                                |

`PaymentRecordFilters`, `PaymentRecordTable`의 내부 `Member` 인터페이스도 동일하게 확장해서 prop이 통과되도록 함.

## 8. 효과

- **운영 순서 의존성 해소**: LEFT 처리 후에도 과거 거래분을 정상 매칭 가능
- **잘못된 후보 제거**: PENDING/REJECTED 회원이 후보에서 제외됨
- **자동 스케일**: 누적 회원이 1,000명+이어도 응답은 그 시점 활동자(보통 100~300명) 수준으로 한정
- **시각 구분**: LEFT 회원이 후보에 있을 때 회색 톤 + `탈퇴 YYYY-MM` 배지로 구분

---

## 9. 향후 검토

- 한 batch가 매우 긴 기간(예: 1년치)을 포함하는 경우, batch 모드의 후보군이 커질 수 있음. 현재는 batch 거래일 min/max를 그대로 쓰지만, 필요해지면 행별 거래일 기반으로 더 좁히는 옵션을 검토.
- 응답 건수가 일정 임계치(예: 300건)를 넘기 시작하면 검색어 서버 푸시다운(name `contains` debounce) + `selectedMemberIds` 별도 보강 로직 추가 검토.
- `/api/clubs/members`의 주석/구현 불일치는 별도 이슈로 정리.
