## 1. 배경 (Why)

기존에는 확정된 입금 내역을 되돌리려면 행 단위 [확정 취소] 버튼을 N번 눌러야 했다. 운영에서 자주 일어나는 패턴은 다음과 같다.

> 잘못 확정된 여러 건(예: 회원 매칭이 틀렸거나 잘못된 월로 확정)을 한꺼번에 되돌리고, 회원·월을 바로잡은 뒤 다시 일괄 확정하고 싶다.

체크박스 다중 선택은 `MATCHED` 탭의 [선택 항목 확정]에는 이미 도입되어 있었지만(→ [입금내역-선택-월지정-일괄확정.md](./입금내역-선택-월지정-일괄확정.md)), `CONFIRMED` 탭에는 일괄 처리 수단이 없어 같은 패턴을 N번 클릭으로 처리해야 했다.

## 2. 도입한 개선

### 2-1. 확정 탭에서 체크박스 다중 선택 → 일괄 확정 취소

UI 흐름:

1. 상태 탭에서 **[확정]** 클릭 → 확정된 입금 내역만 표시
2. 표 헤더와 각 row의 체크박스로 되돌릴 record들을 선택
3. 선택 시 표 위에 파란 툴바가 나타남 — `[선택 항목 확정 취소]` (빨강 버튼)
4. 클릭 → confirm 다이얼로그(N건의 확정을 취소하시겠습니까?) → 결과 alert
5. 결과 alert에 `김철수: 확정 상태가 아닙니다`처럼 입금자명 prefix 포함한 실패 사유 표시

### 2-2. 체크박스 노출 정책 정리

체크박스는 **일괄 동작이 정의된 탭에서만** 노출하도록 정리했다.

| 탭                   | 체크박스 | 일괄 동작               |
| -------------------- | -------- | ----------------------- |
| 전체                 | ❌       | 없음                    |
| 대기 (PENDING)       | ❌       | 없음                    |
| 매칭됨 (MATCHED)     | ✅       | 선택 항목 확정          |
| **확정 (CONFIRMED)** | **✅**   | **선택 항목 확정 취소** |
| 에러 (ERROR)         | ❌       | 없음                    |
| 건너뜀 (SKIPPED)     | ❌       | 없음                    |

이전 문서의 추후 검토 항목("탭이 MATCHED가 아닐 때 체크박스를 숨김 + 탭 전환 시 선택 초기화")을 함께 처리한 결과다.

## 3. 설계 의사결정

### 3-1. "전체 탭에서도 다중 선택"을 지원하지 않은 이유

처음에는 두 가지 안이 있었다.

- **A. 탭 기반 분기**: MATCHED·CONFIRMED 탭에서만 체크박스 노출. 탭이 곧 모드.
- **B. 동질 상태 기반**: 모든 탭에서 체크박스 활성. 선택된 행들의 상태에 따라 액션 바를 동적으로 분기(전부 MATCHED → 확정 / 전부 CONFIRMED → 취소 / 섞임 → 비활성).

운영 관점에서 사용자는 어차피 **"매칭됨/확정 탭으로 좁힌 후 처리"**하는 흐름을 따르므로, B의 "전체 탭에서 동시 작업" 케이스는 거의 사용되지 않을 가능성이 높다. 또한 B는 "섞인 선택" 상태가 가능해지면서 모드 판정·UX가 한 단계 더 복잡해진다. **A로 결정**.

### 3-2. CONFIRMED 행의 "선택"이 갖는 의미는 MATCHED와 다르다

같은 체크박스라도 MATCHED 탭에서의 선택은 "확정 대상", CONFIRMED 탭에서의 선택은 "취소 대상"이다. 탭 전환 시 직전 선택이 따라오면 의도와 다른 일괄 작업으로 이어질 위험이 있어, **statusFilter 변경 시 `selectedRecordIds`를 비우는 effect**를 추가했다.

## 4. 백엔드 처리

### 4-1. 신규 엔드포인트 `POST /api/clubs/[id]/membership-fee/records/bulk-unconfirm`

요청:

```ts
{ recordIds: string[] }
```

응답 (`bulk-confirm`과 형식 통일):

```ts
{
  data: {
    results: {
      success: string[];
      failed: { recordId: string; reason: string }[];
    };
    summary: {
      total: number;     // 요청한 recordIds 갯수
      processed: number; // DB에서 조회된 갯수
      success: number;
      failed: number;
    };
  };
  status: 200;
  message: '${success}건 확정 취소, ${failed}건 실패';
}
```

### 4-2. 처리 로직

1. ADMIN 권한 확인 (기존 `unconfirm.ts`와 동일 패턴)
2. `bulkUnconfirmSchema`로 입력 검증 (`recordIds: z.array(z.string()).min(1)`)
3. `prisma.paymentRecord.findMany`로 `clubId` 일치 record 조회
4. 각 recordId에 대해:
   - 존재하지 않음 → `{ reason: '입금 내역을 찾을 수 없습니다' }` 실패 처리
   - `status !== 'CONFIRMED'` → `{ reason: '확정 상태가 아닙니다' }` 실패 처리
   - 위 둘 통과 → `targetIds`에 push
5. `targetIds`가 있으면 한 트랜잭션 안에서:
   - `membershipPayment.deleteMany({ paymentRecordId: { in } })` — 자동 생성된 납부 레코드 제거
   - `paymentRecord.updateMany({ id: { in }, status: 'CONFIRMED' }, { status: 'MATCHED', errorReason: null })` — race condition 방지를 위해 update 시점에도 `status: 'CONFIRMED'`를 다시 확인

→ 트랜잭션 실패 시 `targetIds` 전체를 동일 사유로 fail 처리.

### 4-3. 단건 vs. 일괄의 차이

기존 단건 `unconfirm.ts`는 record 1건이 CONFIRMED가 아니면 즉시 400을 반환한다(전부 실패 = 호출 자체 실패). 일괄은 사용자가 한 번에 여러 건을 처리하는 운영 흐름이므로, **건별 성공/실패를 results에 누적해 부분 성공을 허용**한다.

### 4-4. 다중 안전망

확정 취소 동작이 CONFIRMED 상태에서만 가능하도록 3중으로 막혀 있다:

1. **프런트 — 탭 분기**: `process.tsx`의 `isBulkSelectionTab = statusFilter === 'MATCHED' || statusFilter === 'CONFIRMED'`. CONFIRMED 탭에서만 체크박스가 노출되고, 그 외 탭에서는 `selectedRecordIds`/`onSelectedRecordIdsChange` prop 자체가 `undefined`로 내려가 체크박스 컬럼이 사라짐.
2. **프런트 — row 체크박스 렌더링**: `PaymentRecordTable`의 `isRecordSelectable`이 `MATCHED + 매칭 회원 있음 || CONFIRMED`만 통과시킴.
3. **백엔드 — record별 status 검증**: `bulk-unconfirm.ts`가 record별로 `status === 'CONFIRMED'`를 검사하고, 트랜잭션 안의 `updateMany`에서도 다시 `status: 'CONFIRMED'` 조건을 건다. 클라이언트가 우회해도 다른 상태 record는 거부된다.

## 5. 프런트 처리

### 5-1. `PaymentRecordTable` 체크박스 활성 조건 확장

```ts
const isRecordSelectable = (r: PaymentRecord) => {
  if (r.status === 'CONFIRMED') return true;
  if (r.status === 'MATCHED' && getRecordMemberIds(r).length > 0) return true;
  return false;
};
```

`selectableRecordIds`(헤더 "전체 선택" 대상)와 row별 `isSelectable` 모두 이 함수를 사용한다.

### 5-2. `process.tsx`

새로 추가한 것:

```ts
const isBulkSelectionTab =
  statusFilter === 'MATCHED' || statusFilter === 'CONFIRMED';

useEffect(() => {
  setSelectedRecordIds([]);
}, [statusFilter]); // 탭 전환 시 선택 초기화

const bulkUnconfirmMutation = useBulkUnconfirmPayments(clubIdStr);

const handleBulkUnconfirmSelected = async () => {
  // confirm() → bulkUnconfirmMutation.mutateAsync({ recordIds })
  // 결과 alert에 입금자명 prefix가 붙은 실패 사유 표시
  // 성공 record는 selectedRecordIds에서 제거
};
```

`PaymentRecordTable`에 prop 전달 시:

```tsx
selectedRecordIds={isBulkSelectionTab ? selectedRecordIds : undefined}
onSelectedRecordIdsChange={
  isBulkSelectionTab ? setSelectedRecordIds : undefined
}
```

`selectedRecordIds`가 `undefined`면 `PaymentRecordTable`의 기존 `isSelectionEnabled` 분기에 의해 체크박스 컬럼·헤더·셀이 모두 자동으로 숨겨진다.

### 5-3. 액션 바 분기 (selectedRecordIds.length > 0일 때만 노출)

```tsx
{statusFilter === 'CONFIRMED' ? (
  // [선택 항목 확정 취소] (빨강) + 안내문구
) : (
  // 연도·월 선택 + [선택 항목 확정] (초록)  ← 기존 흐름
)}
```

CONFIRMED 탭의 안내 문구: "선택한 입금 내역의 확정을 취소합니다. 회원·월 수정 후 다시 확정해야 합니다."

### 5-4. 신규 hook `useBulkUnconfirmPayments`

`useBulkConfirmPayments`와 같은 패턴. `POST /records/bulk-unconfirm` 호출, onSuccess에서 `paymentRecords`·`paymentDashboard` 캐시 invalidate.

## 7. UX 디테일

- 툴바는 `selectedRecordIds.length > 0`일 때만 표시.
- 확정 취소 버튼은 빨강(`bg-red-500`) — 되돌림/파괴적 동작 신호.
- confirm 다이얼로그로 1차 방지: "${N}건의 확정을 취소하시겠습니까? 회원·월 수정 후 다시 확정해야 합니다."
- 실패 결과 alert 형식:

  ```
  3건 확정 취소, 1건 실패

  실패 사유:
  • 김철수: 확정 상태가 아닙니다
  ```

- 탭 전환 시 선택이 자동으로 초기화되므로, "직전 탭에서 체크해 둔 항목이 따라오는" 혼란이 없다.
