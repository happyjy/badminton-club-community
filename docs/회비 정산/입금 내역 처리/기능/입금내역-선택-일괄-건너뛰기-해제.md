## 1. 배경 (Why)

기존에 다중 선택·일괄 처리는 `MATCHED`(선택 항목 확정)·`CONFIRMED`(선택 항목 확정 취소) 두 탭에서만 지원됐다(→ [입금내역-선택-월지정-일괄확정.md](./입금내역-선택-월지정-일괄확정.md), [입금내역-선택-일괄-확정취소.md](./입금내역-선택-일괄-확정취소.md)). 그러나 운영에서 다음 패턴이 자주 일어난다.

- **대기(PENDING) / 에러(ERROR) 탭**: 정산 대상이 아닌 입금건(다른 용도 송금, 환불, 임시 송금 등)이 묶여 들어와 N건을 한 번에 [건너뛰기]로 정리하고 싶다.
- **매칭됨(MATCHED) 탭**: 매칭은 됐지만 이번 정산에서 제외하고 싶은 항목들을 한 번에 [건너뛰기].
- **건너뜀(SKIPPED) 탭**: 잘못 건너뛴 여러 건을 한 번에 되돌리고 싶다.

지금은 모두 행 단위 [건너뛰기]·[건너뜀 해제] 버튼을 N번 눌러야 한다.

## 2. 도입한 개선

### 2-1. 탭별 일괄 동작 추가

| 탭                   | 체크박스 | 일괄 동작                                  |
| -------------------- | -------- | ------------------------------------------ |
| 전체                 | ❌       | 없음 (상태 혼재로 단일 동작 정의 불가)     |
| **대기 (PENDING)**   | ✅       | **[선택 항목 건너뛰기]**                   |
| 매칭됨 (MATCHED)     | ✅       | 선택 항목 확정 / **+ [선택 항목 건너뛰기]** |
| 확정 (CONFIRMED)     | ✅       | 선택 항목 확정 취소 (기존)                 |
| **에러 (ERROR)**     | ✅       | **[선택 항목 건너뛰기]**                   |
| **건너뜀 (SKIPPED)** | ✅       | **[선택 항목 건너뜀 해제]**                |

이전 문서에서 정리한 "한 탭 = 한 일괄 액션" 원칙을 유지하되, MATCHED 탭에 한해 두 액션(확정 / 건너뛰기)을 함께 노출한다. 매칭이 끝난 항목 중 일부를 정산에서 빼고 싶을 때 다시 PENDING/ERROR 탭으로 이동시키는 동선이 부자연스럽기 때문이다.

### 2-2. UI 흐름

1. 상태 탭에서 대기/매칭됨/에러/건너뜀 중 하나 클릭
2. 표 헤더와 각 row의 체크박스로 처리할 record 선택
3. 선택된 항목이 1건 이상이면 표 위에 파란 툴바가 나타남
4. 툴바의 액션 버튼 클릭 → confirm 다이얼로그 → 결과 alert
5. 결과 alert에 `김철수: 이미 확정된 입금 내역은 건너뛸 수 없습니다`처럼 입금자명 prefix 포함한 실패 사유 표시

## 3. 설계 의사결정

### 3-1. 전체 탭에서는 일괄 동작 미지원

전체 탭은 상태가 혼재되어 있어, 선택된 행들의 상태에 따라 액션을 동적으로 바꾸는 분기가 필요하다. [입금내역-선택-일괄-확정취소.md](./입금내역-선택-일괄-확정취소.md) 3-1에서 같은 사유로 한 번 기각된 패턴이며, 이번에도 따라간다. 사용자는 어차피 상태 탭으로 좁힌 후 처리하는 흐름을 따른다.

### 3-2. MATCHED 탭의 두 액션 공존

MATCHED 탭에는 기존 [선택 항목 확정] 옆에 [선택 항목 건너뛰기]를 추가한다. 같은 선택을 두 가지 동작 중 하나로 처리할 수 있다는 의미이며, 사용자는 선택 → 의도에 맞는 버튼 클릭의 흐름을 따른다.

- 확정 버튼: 초록 (`bg-green-500`) — 정산 진행
- 건너뛰기 버튼: 노랑 (`bg-yellow-500`) — 정산 제외 (행 단위 [건너뛰기] 아이콘과 같은 색 계열)

### 3-3. 건너뜀 해제의 복원 상태 (PENDING vs MATCHED)

기존 단건 unskip API(`unskip.ts`)는 매칭 회원 유무에 따라 복원 상태를 분기한다.

- 매칭 회원 있음 → `MATCHED`
- 매칭 회원 없음 → `PENDING`

일괄 unskip도 record별로 같은 분기를 적용한다(한 트랜잭션 안에서 두 그룹으로 나누어 `updateMany` 두 번).

### 3-4. ERROR 상태에서의 건너뛰기 정책

기존 단건 skip API(`skip.ts`)는 `status === 'CONFIRMED'`만 거부하고 그 외 상태는 모두 SKIPPED로 변경 가능하다. 즉 ERROR도 단건 skip은 이미 동작한다. 일괄도 동일하게 "CONFIRMED만 거부"로 통일한다.

## 4. 백엔드 처리

### 4-1. 신규 엔드포인트 `POST /api/clubs/[id]/membership-fee/records/bulk-skip`

요청:

```ts
{ recordIds: string[] }
```

응답 (`bulk-confirm`·`bulk-unconfirm`과 형식 통일):

```ts
{
  data: {
    results: {
      success: string[];
      failed: { recordId: string; reason: string }[];
    };
    summary: {
      total: number;
      processed: number;
      success: number;
      failed: number;
    };
  };
  status: 200;
  message: '${success}건 건너뛰기, ${failed}건 실패';
}
```

처리 로직:

1. ADMIN 권한 확인
2. `bulkSkipSchema`로 입력 검증 (`recordIds: z.array(z.string()).min(1)`)
3. `prisma.paymentRecord.findMany`로 `clubId` 일치 record 조회
4. record별 검증:
   - 존재하지 않음 → `{ reason: '입금 내역을 찾을 수 없습니다' }`
   - `status === 'CONFIRMED'` → `{ reason: '이미 확정된 입금 내역은 건너뛸 수 없습니다' }`
   - `status === 'SKIPPED'` → `{ reason: '이미 건너뛴 입금 내역입니다' }`
   - 위 통과 → `targetIds`에 push
5. `targetIds`가 있으면 `paymentRecord.updateMany({ id: { in }, status: { not: 'CONFIRMED' } }, { status: 'SKIPPED' })` — race condition 방지를 위해 update 시점에도 `status: { not: 'CONFIRMED' }` 재확인

### 4-2. 신규 엔드포인트 `POST /api/clubs/[id]/membership-fee/records/bulk-unskip`

요청·응답 형식은 `bulk-skip`과 동일.

처리 로직:

1. ADMIN 권한 확인
2. `bulkUnskipSchema`로 입력 검증
3. `prisma.paymentRecord.findMany`로 record 조회 (매칭 회원 카운트 포함):

   ```ts
   include: { _count: { select: { matchedMembers: true } } }
   ```

4. record별 검증:
   - 존재하지 않음 → 실패
   - `status !== 'SKIPPED'` → `{ reason: '건너뛰기된 내역만 해제할 수 있습니다' }`
   - 통과 → 매칭 회원 유무에 따라 `toMatched` / `toPending` 그룹으로 분류
5. 한 트랜잭션 안에서 두 `updateMany`:

   ```ts
   await tx.paymentRecord.updateMany({
     where: { id: { in: toMatchedIds }, status: 'SKIPPED' },
     data: { status: 'MATCHED' },
   });
   await tx.paymentRecord.updateMany({
     where: { id: { in: toPendingIds }, status: 'SKIPPED' },
     data: { status: 'PENDING' },
   });
   ```

### 4-3. 다중 안전망

| 단계                | 보장                                                                                                                                                                                                       |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 프런트 — 탭 분기    | `process.tsx`의 `isBulkSelectionTab`이 PENDING/MATCHED/CONFIRMED/ERROR/SKIPPED를 모두 포함하도록 확장. 전체/그 외에는 체크박스 prop 자체를 `undefined`로 내려 컬럼이 사라짐.                                |
| 프런트 — row 렌더링 | `PaymentRecordTable`의 `isRecordSelectable`이 위 5개 상태를 통과시키되 행 자체에서는 의미 있는 액션이 가능한 행만 체크박스 표시 (예: PENDING이지만 ERROR 사유로 잠긴 행은 별도 검토 — 현 정책: 모두 허용). |
| 백엔드 — 상태 검증  | `bulk-skip`은 CONFIRMED를 거부, `bulk-unskip`은 SKIPPED 외 거부. update 시점에도 status 재확인.                                                                                                            |

## 5. 프런트 처리

### 5-1. `PaymentRecordTable` 체크박스 활성 조건 확장

```ts
const isRecordSelectable = (r: PaymentRecord) => {
  if (r.status === 'CONFIRMED') return true;
  if (r.status === 'MATCHED' && getRecordMemberIds(r).length > 0) return true;
  if (r.status === 'PENDING') return true;
  if (r.status === 'ERROR') return true;
  if (r.status === 'SKIPPED') return true;
  return false;
};
```

> 주의: MATCHED는 매칭 회원이 0명인 경우(스토어드 잔재 등) 체크박스를 막지만, PENDING/ERROR/SKIPPED는 회원 매칭 유무와 무관하게 통과시킨다 — 건너뛰기/해제 동작은 회원 정보를 요구하지 않는다.

### 5-3. 액션 바 분기 (selectedRecordIds.length > 0일 때만 노출)

statusFilter별로 액션 바 내용을 분기:

```tsx
{statusFilter === 'CONFIRMED' && (
  // [선택 항목 확정 취소] (빨강) — 기존
)}
{statusFilter === 'MATCHED' && (
  // 연도·월 + [선택 항목 확정] (초록) + [선택 항목 건너뛰기] (노랑)
)}
{(statusFilter === 'PENDING' || statusFilter === 'ERROR') && (
  // [선택 항목 건너뛰기] (노랑)
)}
{statusFilter === 'SKIPPED' && (
  // [선택 항목 건너뜀 해제] (회색/파랑)
)}
```

각 안내 문구:

- PENDING: "선택한 입금 내역을 건너뛰기 처리합니다. 정산 대상에서 제외됩니다."
- MATCHED (건너뛰기 옆에): "정산에서 제외하려면 [선택 항목 건너뛰기]를 사용하세요."
- ERROR: "선택한 입금 내역을 건너뛰기 처리합니다. 에러 사유와 무관하게 정산 대상에서 제외됩니다."
- SKIPPED: "선택한 입금 내역의 건너뛰기를 해제합니다. 매칭 회원이 있으면 매칭됨으로, 없으면 대기로 복원됩니다."

### 5-4. 신규 hook

`useBulkConfirmPayments`·`useBulkUnconfirmPayments`와 같은 패턴.

```ts
useBulkSkipPayments(clubId)   // POST /records/bulk-skip

```

## 7. UX 디테일

- 툴바는 `selectedRecordIds.length > 0`일 때만 표시.
- 건너뛰기 버튼은 노랑 (`bg-yellow-500`) — 행 단위 [건너뛰기] 아이콘 색과 통일, 비파괴적이지만 상태 변경 신호.
- 건너뜀 해제 버튼은 회색 (`bg-gray-500`) — 되돌림 동작.
- confirm 다이얼로그:
  - 건너뛰기: "${N}건을 건너뛰기 처리하시겠습니까? 정산 대상에서 제외됩니다."
  - 건너뜀 해제: "${N}건의 건너뛰기를 해제하시겠습니까?"
- 결과 alert 형식 (실패 사례):

  ```
  3건 건너뛰기, 1건 실패

  실패 사유:
  • 김철수: 이미 확정된 입금 내역은 건너뛸 수 없습니다
  ```

- 탭 전환 시 선택이 자동으로 초기화된다(기존 effect 재사용).

## 9. 검증

- `pnpm lint`
- `npx tsc --noEmit`
- 수동 검증 시나리오:
  - PENDING 2건 선택 → 일괄 건너뛰기 → 둘 다 SKIPPED, 탭 카운트 갱신
  - ERROR + PENDING 혼재(전체 탭): 체크박스 비표시 — 정책상 처리 안 됨
  - SKIPPED 매칭 있음 1건 + 매칭 없음 1건 선택 → 일괄 해제 → 각각 MATCHED / PENDING 으로 복원
  - MATCHED 3건 선택 → [선택 항목 건너뛰기] → 모두 SKIPPED
  - 권한 없는 사용자 호출 → 403
  - 다른 클럽의 recordId 섞기 → "찾을 수 없습니다" 실패
