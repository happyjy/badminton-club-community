# 매칭 단계 부부 배우자 자동 추가

작성일: 2026-05-09
관련 화면: `/clubs/[id]/membership-fee/upload` → `/clubs/[id]/membership-fee/process` (입금 처리 — 매칭 결과 / 일괄 확정)
관련 파일:

- `src/lib/membership-fee/memberMatcher.ts` (`matchDepositor` 시그니처 확장 + `maybeAttachSpouse` 후처리 신설)
- `src/lib/membership-fee/memberMatcher.test.ts` (신규)
- `src/pages/api/clubs/[id]/membership-fee/upload.ts` (의무 정보 함께 로드 + `transactionDate` 전달)

## 1. 배경 (Why)

기존 `matchDepositor`는 **입금자 명에 부부 두 사람 이름이 모두 들어 있을 때만** 부부 매칭(`matchType: 'couple'`)으로 떨어졌다. 한 사람 이름만 있으면 본인 1명만 매칭되어, 운영자가 회비 처리할 때 다음 흐름이 반복됐다:

1. 부부 회비(예: 45,000원) 입금이 본인 1명 매칭으로 표시됨
2. 일괄 확정에서는 "1명 + 부부 단가"로 인식되어 **본인만 납부 처리**
3. 배우자는 미납으로 남아 운영자가 매번 재매칭 UI에서 손으로 추가

부부가 한 사람 이름으로만 입금하는 게 일반적이라, 이 수동 작업이 매월 누적되었다.

다만 단순히 "부부 그룹이면 무조건 둘 다 추가"로 하면 다음 케이스가 깨진다:

- 배우자가 **휴회·병가** 중인 달의 입금
- 배우자가 **탈퇴**한 뒤의 입금
- 배우자가 **아직 가입 전**(부부가 따로 가입)인 시점의 입금

이런 상황에서 강제로 둘 다 매칭하면 일괄 확정에서 "의무월 아님" 사유로 실패하거나, 더 나쁘게는 의무 없는 월에 납부 기록이 생긴다. 그래서 **입금일 시점의 의무 상태**를 매칭 단계에서 검증하는 자동 추가 로직이 필요했다.

## 2. 도입한 개선

### 2-1. `matchDepositor`에 `transactionDate` 인자 추가

```ts
matchDepositor(
  depositorName: string,
  members: Member[],
  coupleGroups: CoupleGroup[] = [],
  transactionDate: Date | null = null
): MatchResult
```

- 인자는 옵셔널이라 다른 호출처(현재 없음)·테스트의 하위 호환은 유지.
- `null`이면 기존 동작과 동일(의무 검증 없이 부부 그룹 소속만으로 자동 추가) — 폴백 안전망.

### 2-2. exact / partial 매칭 후 `maybeAttachSpouse` 후처리

`memberMatcher.ts`의 1단계(exact), 3단계(이름 포함 partial), 4단계(성 제외 partial) 매칭 결과에 후처리를 통과시킨다:

```ts
function maybeAttachSpouse(
  baseResult: MatchResult,
  coupleGroups: CoupleGroup[],
  transactionDate: Date | null
): MatchResult
```

판정 순서:

1. 매칭된 본인이 부부 그룹 소속인지 확인 (소속 아니면 그대로 반환)
2. 본인이 입금일 속한 연·월에 `isMonthObligated`로 의무인지 확인 (아니면 그대로 — 본인 명의 입금이지만 휴회 중일 수 있는 케이스 보호)
3. 배우자가 같은 월 의무인지 확인 — 의무인 배우자만 골라 `memberIds`에 합류
4. 배우자가 한 명이라도 통과하면 `matchType: 'couple'`로 격상하고 `memberIds = [본인, ...의무 배우자들]`

의무 판정은 기존 `feeObligation.ts`의 `isMonthObligated`를 그대로 재사용 — 가입일·휴회·탈퇴 정책이 기존 대시보드/차기월 추천과 동일한 함수에서 결정되므로 정책 비대칭이 생기지 않는다.

### 2-3. `couple` 격상 단계 (2단계·6단계) 영향 없음

기존 2단계(두 이름 모두 포함)·6단계(부부 그룹 단일 정확 일치)는 후처리를 거치지 않는다. 2단계는 이미 두 사람을 묶어 반환하므로 자동 추가 대상이 아니고, 6단계는 가능한 한 보수적으로 둔다(드물게 가는 분기라 후처리로 격상하면 오작동 위험만 높아짐).

### 2-4. 5단계(2글자 성 생략)·7단계(유사도) 미적용

운영 중에 오매칭이 가장 빈번한 두 단계라, 자동 추가까지 적용하면 잘못된 회원 + 그 배우자 두 명에게 동시에 영향이 가는 위험이 커진다. 이 두 단계는 본인 1명만 매칭으로 두고, 필요 시 운영자가 수동 추가하는 기존 흐름을 유지한다.

### 2-5. `upload.ts` — 의무 정보 함께 로드

`coupleGroup` 조회에 `feeObligationStartAt`/`leftAt`을 포함하고, 부부 그룹 소속 회원의 `MemberLeave`를 별도 쿼리로 가져와 멤버에 매핑:

```ts
const coupleGroupsRaw = await prisma.coupleGroup.findMany({
  where: { clubId: clubIdNumber },
  include: {
    members: {
      include: {
        clubMember: {
          select: {
            id: true, name: true,
            feeObligationStartAt: true,
            leftAt: true,
          },
        },
      },
    },
  },
});
const coupleLeaves = await prisma.memberLeave.findMany({
  where: { clubMemberId: { in: coupleMemberIds } },
});
// → leaveMap에 합쳐 coupleGroups[].members[].clubMember.leavePeriods로 전달
```

이후 매칭 호출에 `row.transactionDate`를 함께 넘긴다. 추가 쿼리는 1건(부부 멤버 휴회 조회)뿐이고, `coupleMemberIds`가 비면 호출 자체를 건너뛴다.

`matchDepositor`의 다른 호출처는 없다(`unconfirm`/`unskip`/`bulk-unskip`은 status만 되돌리고 기존 `matchedMembers`를 유지하는 흐름). 즉 시그니처 변경의 영향은 `upload.ts` 한 곳.

### 2-6. 일괄 확정 단계 영향

`bulk-confirm.ts`는 이미 `isFullCoupleMatch` 분기로 부부 단가(coupleAmount)를 1회만 합산하고 인원 수로 균등 분배한다 — 매칭 단계에서 두 명이 들어오면 이 분기가 자동으로 동작하므로 `bulk-confirm.ts` 코드는 변경 없음.

## 3. 의사결정

| 결정 | 이유 |
| --- | --- |
| 매칭 단계에서 추가 (일괄 확정 단계 아님) | UI 표시·재매칭·일괄 확정 등 모든 후속 흐름이 일관되게 "관계 매칭 2명"을 보게 됨. 한 곳만 손보면 끝 |
| 입금일 속한 연·월 기준으로 의무 판정 | 매칭 시점에는 어느 월 회비인지 모르지만, 입금일 자체가 가장 합리적인 추정값. 자동 월 추천 로직과도 일관 |
| 의무월 어긋날 때는 자동 추가 안 함 (가능한 사람만) | 본인은 의무인데 배우자는 휴회/미가입/탈퇴면 본인 1명만 — 일괄 확정 흐름이 끊기지 않음 |
| exact + partial까지만 적용 (similar 제외) | similar(Levenshtein ≤1) 매칭은 오매칭이 잦아, 자동 추가까지 적용하면 잘못된 회원 + 배우자 두 명에 영향 |
| 본인이 그 월 의무 아니어도 본인 매칭은 유지 | 휴회 중인 본인 명의 입금은 드물지만 가능 — 매칭 자체를 끊으면 운영자가 더 헷갈림. 다만 그 경우 배우자만 자동 추가하지는 않음 |
| `transactionDate` 옵셔널 | 테스트·미래 호출처에서 의무 검증을 끄고 사용할 여지 + 점진적 도입 |

## 4. 검증

`memberMatcher.test.ts` 신규 — 10개 케이스 모두 통과:

- 본인 exact + 배우자 의무 → couple 격상 + `memberIds: [1, 2]`
- 본인 partial(이름 포함) + 배우자 의무 → couple 격상
- 본인 partial(성 제외) + 배우자 의무 → couple 격상
- 배우자 탈퇴 → 본인 1명 유지
- 배우자 휴회 중 → 본인 1명 유지
- 배우자 가입일이 입금일 이후(미가입) → 본인 1명 유지
- 본인이 휴회 중 → 본인 1명 유지(배우자도 자동 추가 안 함)
- 부부 그룹 미소속 → 단독 유지
- 두 사람 이름 모두 포함된 입금자 명 → 기존 2단계 부부 매칭 유지(후처리 무관)
- `transactionDate` 미전달 → 의무 검증 없이 부부 자동 추가 (하위 호환)
