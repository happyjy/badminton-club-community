## 1. 배경 (Why)

입금 내역 처리 화면의 [확정] 모달은 매칭 회원의 마지막 납부월 기준으로 "차기월(권장)"을 표시하고 기본 선택값으로 채워준다. 기존 구현은 클라이언트가 단순히 `lastPaid + 1개월`로 계산했기 때문에 **휴회/병가 기간이 무시**되는 문제가 있었다.

예시: 회원이 1월 납부 후 3~5월 병가인 경우

- 사용자 기대: "차기월(권장): 6월"
- 기존 동작: "차기월(권장): 2월" (정상)
- 결정적 버그: 2월이 last paid이고 3~5월이 병가면 "차기월(권장): 3월" — **병가 월이 추천됨**

같은 시스템의 다른 화면(대시보드, 미납자, 일괄 확정 API, 단건 확정 API)은 모두 `getObligationMonths` / `isMonthObligated`로 휴회를 제외하는데, 입금 처리 화면의 권장 표시만 휴회를 반영하지 않아 비대칭 상태였다.

## 2. 원인

`PaymentRecord` 응답에는 차기월을 정확히 계산할 수 있는 회원의 휴회/탈퇴 정보가 포함되지 않았다.

| 데이터                  | 백엔드 보유 | PaymentRecord 응답 |
| ----------------------- | ----------- | ------------------ |
| `lastPaidYearMonth`     | ✅          | ✅ (이전부터 첨부) |
| `feeObligationStartAt`  | ✅          | ❌                 |
| `leavePeriods`          | ✅          | ❌                 |

따라서 클라이언트가 차기월을 계산할 데이터 자체가 부족했고, `lastPaid + 1`로 fallback할 수밖에 없었다.

## 3. 도입한 개선

### 3-1. `getNextObligatedMonth` 헬퍼 추가

`src/lib/membership-fee/feeObligation.ts`에 다음 시그니처의 함수를 추가:

```ts
getNextObligatedMonth(
  lastPaid: { year: number; month: number } | null,
  feeObligationStartAt: Date | null,
  leavePeriods: LeavePeriod[],
  leftAt?: Date | null
): { year: number; month: number } | null
```

- `lastPaid` 다음 달부터 시작해, **휴회/탈퇴 제외** 후 첫 의무월을 반환.
- `lastPaid`가 없으면 `feeObligationStartAt`이 속한 월부터 탐색.
- 탐색 상한 24개월 — 휴회 종료 미정인 경우 무한 루프 방지.
- 탈퇴월 이후거나 24개월 내 의무월이 없으면 `null` 반환.

### 3-2. records GET 응답에 `nextSuggestedYearMonth` 첨부

`attachLastPaidYearMonth`를 확장해 회원별 `feeObligationStartAt` / `leftAt` / `MemberLeave` 도 한 번에 조회하고, record마다 `nextSuggestedYearMonth`를 함께 첨부한다.

추가 쿼리(record 응답 1회 호출당):

| 쿼리                            | 비고                              |
| ------------------------------- | --------------------------------- |
| `prisma.clubMember.findMany`    | id 매칭, 의무 시작일·탈퇴일만 select |
| `prisma.memberLeave.findMany`   | clubMemberId 매칭, 모든 휴회 row |

기존 `prisma.membershipPayment.findMany`와 함께 `Promise.all`로 병렬 실행. 회원 ID 단일 set으로 중복 제거되어 추가 비용은 무시할 수준이다.

### 3-3. 다중 매칭 시 정책

부부처럼 한 입금에 여러 회원이 매칭된 경우, **가장 이른 차기 의무월**을 채택한다 — 한 명이라도 미납이면 그 사람 기준의 다음 의무월을 추천하는 게 사용자 의도에 맞다.

### 3-4. 프런트 사용

`PaymentRecordTable.tsx`의 두 호출부 모두 백엔드 값을 우선 사용, 없으면 기존 `+1개월` fallback:

```ts
const nextDefault =
  record.nextSuggestedYearMonth ??
  (lastPaid ? getNextMonth(lastPaid) : null);
```

## 4. 의사결정

| 결정                                  | 이유                                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------------ |
| 백엔드에서 계산해 첨부 (vs 프런트 계산) | 회원 메타(휴회/시작일)를 record마다 들고 가는 페이로드 비용보다, record당 1회 계산이 단순. `attachLastPaidYearMonth`의 기존 패턴과 일관 |
| `attachLastPaidYearMonth`에 통합 (vs 별 함수) | 동일한 회원 ID set을 두 번 조회하지 않도록. 호출부 2곳(records GET, upload)이 동일하게 모두 차기월을 필요로 함 |
| 24개월 탐색 상한                       | 종료 미정 휴회로 무한 루프 방지. 24개월 내 의무월이 없는 회원은 추천 자체가 의미 없음        |
| fallback `+1개월` 유지                 | 응답이 옛 버전이거나 회원 매칭이 비어있는 경우의 안전망                                     |

## 5. 검증

`feeObligation.test.ts`에 8개 케이스 추가:

- `lastPaid` 다음이 의무월이면 그대로
- `lastPaid` 다음이 휴회 월이면 휴회 종료 직후 의무월
- 12월 → 다음 해 1월
- 12월 + 다음 해 1~2월 휴회 → 3월
- `lastPaid` 없음 + `feeObligationStartAt` 기준
- 시작 월이 휴회면 휴회 이후 첫 의무월
- 탈퇴월 이후 → null
- 종료 미정 휴회로 24개월 내 의무월 없음 → null

전체 24개 케이스 통과.
