## 1. 배경 (Why)

- **재무가 5월부터 이 화면을 쓰지 않았다.**
  - 통장 파일(2026-01-01 ~ 10-03, 입금 649건) 중 425건이 DB에 없었다.
  - 5월 이후 파일에 몰린 패턴을 기존 구조가 받아내지 못했다.
- **모든 입금을 회비로 가정했다.**
  - 뒷풀이·단체티 137건이 "매칭됨(부족)"으로 들어와 하나씩 건너뛰어야 했다.
  - 실수로 확정하면 15,000원이 그 달 회비로 잡혔다.
- **연납·합산 입금을 잘못 셌다.**
  - 275,000원 연회비는 11개월로, 125,000원(가입비 + 1개월)은 5개월로 제안됐다.
  - 단가 판정이 업로드·단건 확정·일괄 확정 세 군데에서 각자 달랐다.
- **입금자가 적은 달을 버렸다.**
  - 입금자명 약 260건에 "3월", "1,2월", "6~9월"이 적혀 있었지만 "마지막 납부월 + 1"만 썼다.
- **카카오뱅크 메모는 없어질 예정이다.**
  - 재무가 앱에서 손으로 적던 정산 기록(월 지정, 오타 교정, "가입비+1월")을 시스템이 맡아야 한다.

## 2. 도입한 개선

- **통장 엑셀을 올리면 회비가 아닌 건은 스스로 빠지고, 회비는 회원·개월 수·달이 정해진다.**
  - 재무는 "검토 필요" 건만 보고 나머지는 일괄 확정 한 번으로 끝낸다.
- **판정은 한 곳에서 한다.**
  - 업로드·조회·단건 확정·일괄 확정이 같은 함수(`planRecord`)로 단가·개월 수·달을 정한다.
  - 화면에 보이는 배정과 확정 결과가 다를 수 없다.

### 2-1. 판정 순서

| 단계 | 모듈 | 하는 일 |
| --- | --- | --- |
| 중복 제외 | `duplicateDetector` | 거래일시(초) + 금액 + 입금자명이 같은 행은 이미 올라온 거래로 보고 뺀다 |
| ① 분류 | `transactionClassifier` | 회비·가입비·행사·기타·이자로 나눈다. 가입비 + 회비는 한 건 안에서 금액을 나눈다 |
| ② 매칭 | `memberMatcher` + `matchableMembers` | 거래일에 활동 중이던 회원만 후보로, 이름 토큰으로 비교한다 |
| ③ 단가·개월 수 | `feeAmountResolver` | 일반·부부·연납 단가를 한 규칙으로 판정한다 |
| ④ 납부월 | `monthHintParser` + `monthAssigner` | 입금자가 적은 달을 우선하고, 없으면 밀린 달부터 채운다 |
| 저장 | `uploadPipeline` → `upload.ts` | 배치·레코드·매칭 회원을 한 트랜잭션으로 저장한다 |

### 2-2. 분류 규칙 (위에서부터 먼저 맞는 것)

| 조건 | 결과 |
| --- | --- |
| 거래구분이 `예금이자` | 이자 |
| 행사·기타 글자와 회비 표시(회비·월비·월)가 함께 있고 한 달 단가 이상 | 회비 + 검토 필요 (금액을 나누라고 안내) |
| 이름만 적어 보낸 한 달 단가 이상의 돈에 메모로만 '콕'이 달림 | 회비 + 검토 필요 |
| 행사 글자(뒷풀이·뒤풀이·뒷풀·회식·월례회·단체티·단체복·대회·참가비, 이름 뒤의 '티')가 입금자명이나 메모에 있음 | 행사 |
| 콕·찬조가 입금자명이나 메모에 있음 | 기타 |
| 가입비 금액과 같고 '가입' 표기가 있거나 회비 표시가 없음 | 가입비 |
| 연납 금액 | 회비 |
| 가입비 + 회비 단가의 배수 | 회비, 회비가 아닌 금액 = 가입비 |
| 회비 단가의 배수 | 회비 |
| 그 밖 (한 달 단가보다 적거나 배수가 아님) | 회비 + 검토 필요 |

- **글자 목록은 `transactionClassifier.ts`의 `EVENT_KEYWORDS`·`OTHER_KEYWORDS`에 있고, 운영하며 늘린다.**
- **표시 없이 몰려 들어온 행사 입금도 잡는다.**
  - 단가의 배수가 아닌 같은 금액이 7일 안에 5건 이상이면 행사로 본다.
  - 그 기간에 들어온 그 금액의 2~4배(여러 명 몫을 한 사람이 낸 것)도 함께 묶는다.
  - 근거를 `kindReason`에 "같은 금액 15,000원 5건이 몰려 들어옴"처럼 남긴다.
- **그 배수가 회비 단가의 배수이기도 하면 어느 쪽으로도 단정하지 않는다.**
  - 15,000원 행사의 세 명 몫 45,000원은 부부 한 달 단가와 같다.
  - 행사로 건너뛰면 부부의 회비가 사라지고, 회비로 확정하면 행사비가 회비로 잡힌다.
  - 회비로 두되 "행사비면 분류를 바꾸고, 회비면 개별 확정하세요"라는 검토 표시를 저장한다.
- **금액만으로 추정한 가입비는 누가 냈는지 본 뒤에 확정한다.**
  - 100,000원은 신규 회원에게는 가입비지만 기존 회원에게는 넉 달 치 회비다.
  - 매칭된 회원이 신규(의무 시작월 ±1개월)가 아니면 회비로 되돌린다.

### 2-3. 매칭

- **후보는 거래일에 활동 중이던 회원뿐이다.**
  - 의무 구간의 앞뒤 한 달은 봐준다(신규 회원의 선납, 탈퇴 회원의 마지막 달 후납).
  - 탈퇴·거절 회원에 매칭되던 64건이 사라진다.
- **이름은 토큰으로 비교한다.**
  - 입금자명에서 숫자·'월'·'회비'·'가입비'·구두점을 떼고 남은 한글이 이름 토큰이다.
  - 유사 매칭은 2~3자 토큰에만 쓰고, 신뢰도 0.8 미만이면 "회원을 확인해주세요"로 검토에 올린다.
- **같은 이름의 회원이 둘 이상이면 한 명에 붙이되 반드시 확인받는다.**
  - 이름만으로는 누구의 돈인지 알 수 없다. "같은 이름의 회원이 2명 있습니다 — 회원을 확인해주세요".
  - 상세 시트에서 회원을 고르거나 "이 회원이 맞음"을 눌러야 일괄 확정 대상이 된다.
- **자동으로 붙인 배우자는 금액이 개인 단가의 배수면 뗀다.**
  - 부부 중 한 사람이 자기 몫만 내는 입금이 매달 "부족"으로 잡히지 않는다.

### 2-4. 월 힌트와 납부월 배정

- **읽는 꼴**: "3월", "1,2월", "1/2월", "6~9월", "1월-4월", "45월"(4·5월), "6회비".
- **연도는 거래일로 정한다.**
  - 첫 달이 거래월에서 3개월 이내로 앞이면 선납, 그 밖이면 밀린 달로 본다.
  - 나머지 달은 적힌 순서대로 잇는다.
- **힌트가 금액·의무·납부 이력과 맞을 때만 쓴다.**
  - 개월 수가 다르거나, 의무월이 아니거나, 이미 낸 달이면 검토 사유를 남기고 밀린 달부터 채운다.
- **힌트가 없으면 그 해의 밀린 달 → 거래월 이후 → 다음 해 순서로 채운다.**
  - 전년으로는 거슬러 가지 않는다(시스템 도입 전 납부는 기록이 없어 모두 미납으로 보인다).
  - 힌트 없이 3개월 이상 앞의 달로 배정되면 선납이 맞는지 확인하게 한다.
- **거래일시·거래월은 한국 시각으로 고정한다.**
  - 서버(Vercel)는 UTC라 매월 1일 0~9시 입금이 전달로 읽히던 문제를 `kst.ts`로 막았다.

## 3. 설계 의사결정

| 결정 | 이유 | 버린 대안 |
| --- | --- | --- |
| 배정할 달과 검토 사유를 저장하지 않고 조회할 때마다 다시 계산한다 | 재무가 휴회·의무 시작월·회비가 아닌 금액을 고치면 그 건을 다시 건드리지 않아도 검토가 풀린다 | 업로드 때 계산해 저장 — 고칠 때마다 다시 저장해야 하고 낡은 사유가 남는다 |
| 저장하는 `needsReview`는 "사람이 확인해야만 풀리는 표시"만 뜻한다 (비슷한 이름·동명이인·행사비일 수 있는 금액). 사유는 `reviewReason` | 다시 계산할 수 없거나, 다시 계산하면 사람의 확인이 지워지는 정보만 저장한다 | 모든 검토 사유를 저장 |
| 같은 회원·같은 달의 중복 납부는 확정 트랜잭션 안에서 막는다 (회원 행 잠금 + 다시 읽기) | 부족분을 채우는 두 번째 납부를 허용하려고 DB의 unique를 뺐다. 판정은 트랜잭션 밖에서 하므로, 저장 직전에 다시 보지 않으면 두 입금이 같은 달로 동시에 확정될 수 있다 | unique 유지 — 부족분 충당을 표현할 수 없다 |
| 분류를 회비로 되돌리면 입금자명으로 회원을 다시 찾는다 | 행사·기타로 분류된 건은 업로드 때 매칭하지 않아 회원이 비어 있다. 다시 찾지 않으면 되돌린 건마다 회원을 손으로 골라야 한다 | 저장된 회원만 본다 |
| 같은 회원의 열린 입금은 거래일 순으로 달을 차례로 배정한다 | 일괄 확정이 그 순서로 확정하므로 화면의 미리보기와 결과가 같다 | 건마다 따로 배정 — 두 건이 같은 달을 가리킨다 |
| 한 입금의 금액을 `nonFeeAmount`로 나눈다 | 가입비 + 1개월, 회비 + 콕을 한 건으로 처리한다 | 레코드를 둘로 쪼갬 — 통장과 건수가 달라진다 |
| 올해 단가가 없으면 직전 연도 단가로 판정하고 그 사실을 알린다 | 1월 파일이 새 해 단가 등록 전이라 막히는 일을 없앤다 | 업로드를 거부 |
| 면제 회원도 실제로 낸 달은 완납으로 본다 | 연중에 임원이 된 회원, 연회비를 낸 회장의 표가 재무의 표와 같아진다 | 면제면 납부를 무시 |
| 메모로만 '콕'이 달린 한 달 단가 이상의 입금은 건너뛰지 않는다 | 회비에 콕 값을 얹어 보낸 돈이라, 건너뛰면 그 달 회비가 조용히 사라진다 | 글자가 있으면 무조건 기타 |

## 4. 백엔드 처리

- **업로드 (`upload.ts`)**
  - 파싱 → 중복 제외 → `judgeUploadRows`(순수 함수) → 한 트랜잭션 저장.
  - 응답 `summary`에 분류별 건수, `confirmable`(바로 확정 가능), `needsReview`, `duplicates`, `ratesFallback`을 싣는다.
- **조회 (`records/index.ts`)**
  - `annotateRecords`가 레코드마다 `suggestedSelections`, `needsReview`, `reviewReasons`, `suggestedStartMonth`, `partialPaidMonth`를 붙인다.
- **단건 수정 (`records/[recordId]` PUT)**
  - 분류, 회비가 아닌 금액과 그 성격, 메모를 고친다.
  - 분류나 열린 회비 건의 회원·금액이 바뀌면 `judgeStoredState`로 상태를 다시 정한다.
  - 분류를 회비로 되돌렸는데 매칭 회원이 없으면 입금자명으로 다시 찾는다(`rematchMembers`).
  - 확정된 건은 메모만 고칠 수 있다. 상태(`status`)는 이 API로 직접 바꿀 수 없다.
  - 읽은 뒤 다른 요청이 그 건을 확정·건너뛰었으면 고치지 않고 "그사이 바뀐 입금 내역입니다"로 알린다.
- **확정 (`confirm.ts`, `bulk-confirm.ts`)**
  - 둘 다 `planRecord`를 쓴다. 건너뛴 건·회비가 아닌 건은 확정할 수 없다.
  - 일괄 확정은 검토가 필요한 건을 실패로 돌려준다.
  - 달을 지정한 일괄 확정은 달에 관한 검토(월 힌트·선납)는 넘어가지만, 저장된 검토 표시와 면제 회원 매칭은 그대로 막는다.
  - 저장 직전에 트랜잭션 안에서 그 건이 아직 매칭됨인지, 그 회원의 그 달이 아직 비어 있는지 다시 본다(`applyPlan`). 어긋나면 400으로 사유를 알린다.
  - 고른 달보다 많이 들어온 금액은 초과 입금으로 기록하고, 확정을 취소하면 되돌린다.
- **선택 항목 분류 변경 (`records/bulk-set-kind.ts`)**
  - `{ recordIds, kind }`. 단건 수정과 같은 규칙으로 상태를 정하고, 회비로 되돌릴 때 회원도 다시 찾는다.
  - 확정된 건, 이미 그 분류인 건은 실패로 돌려준다. 응답은 일괄 처리 형식이다.
- **남은 일 (`dashboard.ts`의 `latestUpload.pendingWork`)**
  - 열려 있는 회비 건을 다시 판정해 미확정·미매칭·검토 필요 건수를 낸다.

| `PaymentRecord` | `needsReview`, `reviewReason` | 사람이 확인해야 풀리는 검토 표시와 그 사유 |
| `PaymentRecord` | `note` | 재무 메모 |
| `MembershipPayment` | `(clubMemberId, year, month)` 유니크 → 일반 인덱스 | 같은 달의 부족분을 나중에 채우는 두 번째 납부를 허용 |

- 마이그레이션: `prisma/migrations/20261010120000_payment_record_kind_and_member_position/migration.sql`.

## 5. 프런트 처리와 UX 디테일

- **업로드 화면은 올린 뒤 바로 다음 일을 하게 한다.**
  - 요약에 분류별 건수, "이미 올라온 N건 제외", 직전 연도 단가로 판정한 사실을 보인다.
  - 버튼 둘: "N건 일괄 확정", "검토 필요 N건 보기"(처리 화면에 배치·검토 필터가 걸린 채로).
- **처리 화면의 표는 왜 멈췄는지를 보여 준다.**
  - 분류 칩, "검토 필요" 칩과 그 사유, 금액 나눔("회비 25,000원 + 가입비 100,000원").
  - 회비가 아닌 건의 매칭 회원 칸은 '-'다. 빨간 "미매칭"은 회원을 찾아야 하는 회비 건에만 쓴다.
  - 필터: 분류, "검토 필요만". 주소 `?batchId=&review=1&kind=`로 바로 들어올 수 있다.
  - 일괄 확정 대상은 매칭됨 + 회비 + 검토 불필요이고, 빠진 건수를 "검토 필요 N건 제외"로 알린다.
- **상세 시트에서 한 번에 고친다.**
  - 매칭 회원과 납부월이 먼저, 그 아래 분류·회비가 아닌 금액·메모.
  - 빠른 선택: 적힌 달, 밀린 달부터, 부족분 채우기, 의무 시작월 앞당기기, "이 회원이 맞음".
- **선택 항목 분류 변경**
  - 선택 막대의 버튼 → 분류 다섯 가지를 고르는 시트 → 확인창.
  - 선택 막대가 화면 아래에 붙어 있어 메뉴 대신 시트를 쓴다.
- **대시보드의 최근 업로드 카드에 남은 일을 보인다.**
  - "미확정 N건 · 미매칭 N건 · 검토 필요 N건". 누르면 그 건들만 걸러진 처리 화면으로 간다.
