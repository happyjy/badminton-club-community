## 1-1. 화면 구성

디자인 시스템의 관리용 화면 틀을 따른다. 결정의 배경은 [`./기능/디자인-시스템-전환.md`](./기능/디자인-시스템-전환.md).

```
PageHeader  "입금 내역 처리"
거래일 범위 줄                     ← 배치로 들어오지 않았을 때
Notice "배치 필터 적용 중" [배치 삭제]  ← 배치로 들어왔을 때
상태 탭 (전체·대기·매칭됨·확정·에러·건너뜀, 건수 포함)
Toolbar  [연도] "N건 표시 중" "검토 필요 N건 제외" [매칭된 항목 일괄 확정]
필터 (입금자명·금액·매칭 회원·분류·검토 필요만)
PaymentRecordsView  표(PC) / 리스트(휴대폰) → 행을 누르면 상세 시트
BulkActionBar  "N건 선택됨" [탭별 일괄 동작] [선택 항목 분류 변경]
```

- **표는 왜 멈췄는지를 보여 준다.** 상태 칩 옆에 분류 칩과 "검토 필요" 칩, 그 아래 사유. 회비가 아닌 건의 매칭 회원 칸은 '-'다.
- **주소로 걸러진 채 들어올 수 있다.** `?batchId=`(배치), `?status=`(상태 탭), `?review=1`(검토 필요만), `?kind=`(분류).

- **한 건 동작은 모두 상세 시트에서 한다.** 표의 행에는 동작 버튼이 없다.
- **일괄 선택은 PC 표에서만 된다.** 휴대폰 리스트에는 체크박스가 없다.
- **정렬은 표의 머리글을 눌러서 한다.** 기본은 거래일 내림차순이다.
- **확인은 `useConfirm`, 결과는 `toast`.** 일괄 결과에 실패가 있으면 사유 목록을 확인창으로 보여 준다. `alert()`·`confirm()`은 쓰지 않는다.

## 2. 구현 완료된 기능

- **자동 판정 파이프라인** — 통장 엑셀을 올리면 회비가 아닌 건은 스스로 빠지고, 회비는 회원·개월 수·달이 정해진다
  - 순서: 중복 제외 → 분류 → 거래일 시점의 회원 매칭 → 단가·개월 수 → 납부월
  - 배정할 달과 검토 사유는 저장하지 않고 조회할 때마다 다시 계산한다 (휴회·시작월을 고치면 검토가 풀린다)
  - 업로드·단건 확정·일괄 확정이 같은 함수(`planRecord`)로 판정한다
  - 상세 기획·스펙: `./기능/자동-분류-월힌트-단가통일.md`
- 엑셀 업로드 → 회원 매칭(이름 토큰 기준: 정확, 부부, 부분, 유사도. 유사 매칭은 "회원을 확인해주세요"로 검토에 올린다)
- **매칭 단계 부부 배우자 자동 추가** — 입금자 명에 부부 중 한 사람만 있어도 매칭 단계에서 배우자를 자동으로 같이 매칭
  - 적용 단계: exact(1단계), partial(3·4단계). similar(7단계)는 오매칭 위험으로 제외
  - 입금일 속한 연·월 기준으로 본인·배우자 모두 의무월일 때만 추가 (배우자가 휴회·미가입·탈퇴면 본인 1명만 유지)
  - `bulk-confirm.ts`는 변경 없음 — 매칭에 두 명이 들어가면 기존 `isFullCoupleMatch` 분기가 자동 동작
  - 상세 기획·스펙: `./기능/매칭-부부-배우자-자동추가.md`
- 가입비(FeeType "가입비")는 분류가 '가입비'인 건너뜀으로 저장한다. 가입비 + 회비를 한 번에 낸 건은 회비로 두고 가입비만큼을 "회비가 아닌 금액"으로 나눈다
- 회비 유형 관리(FeeType CRUD), 월·연납만(분기·반기 주석 처리)
- 회비 금액 관리(FeeRate) - 유형별·연도별·주기별 설정
- 확정 시 연도 선택(전년/당년/내년) + 다중 연도·월 선택 지원
- 월 선택: 단일 / Ctrl+토글 / Shift+범위 선택·해제
- 확정 취소(unconfirm), 건너뛰기(skip/unskip) 지원
- **체크박스 다중 선택 + 탭별 일괄 동작** — 상태 탭에서 record를 골라 한 번에 처리
  | 탭                 | 일괄 동작                                       | 관련 문서                                                                                  |
  | ------------------ | ----------------------------------------------- | ------------------------------------------------------------------------------------------ |
  | 전체               | (없음 — 상태 혼재로 단일 동작 정의 불가)        | —                                                                                          |
  | 대기 (PENDING)     | 선택 항목 건너뛰기 / 분류 변경                  | `./기능/입금내역-선택-일괄-건너뛰기-해제.md`                                               |
  | 매칭됨 (MATCHED)   | 선택 항목 확정 (지정 월) / 선택 항목 건너뛰기 / 분류 변경 | `./기능/입금내역-선택-월지정-일괄확정.md`, `./기능/입금내역-선택-일괄-건너뛰기-해제.md` |
  | 확정 (CONFIRMED)   | 선택 항목 확정 취소                             | `./기능/입금내역-선택-일괄-확정취소.md`                                                    |
  | 에러 (ERROR)       | 선택 항목 건너뛰기 / 분류 변경                  | `./기능/입금내역-선택-일괄-건너뛰기-해제.md`                                               |
  | 건너뜀 (SKIPPED)   | 선택 항목 건너뜀 해제 (회비 분류만, 회원 유무에 따라 복원) / 분류 변경 | `./기능/입금내역-선택-일괄-건너뛰기-해제.md`                              |
  - 탭 전환 시 `selectedRecordIds`는 자동 초기화 (탭마다 선택의 의미가 다름)
  - 별도로 [매칭된 항목 일괄 확정] 버튼은 필터된 MATCHED 중 **회비이고 검토가 필요 없는 건**을 자동 배정 월로 일괄 확정 (체크박스와 별개 흐름). 빠진 건수는 "검토 필요 N건 제외"로 알린다
  - **선택 항목 분류 변경**: 표시 없이 들어온 행사 입금을 금액 필터로 모아 한 번에 '행사'로 바꾸는 용도. 회비가 아닌 분류로 바꾸면 건너뜀, 회비로 바꾸면 매칭 회원 유무에 따라 매칭됨·대기가 된다 — `./기능/자동-분류-월힌트-단가통일.md` §4
- 부족/초과 입금 처리 (부족 시 균등 배분·나중에 부족분 채우기, 초과 시 초과 입금으로 기록) — §6
- **회비 의무 시작 규칙**: 시작월 기준 (15일 규칙에서 변경), `feeObligationStartAt` 기반
- **휴회/병가**: MemberLeave 등록, 의무 월에서 제외, 대시보드 표시
- **회비 관리 대시보드** – 회원별 납부 현황 테이블 필터(입금 확정 결과 집계 기준)
  - UI: 세그먼트 버튼 **전체 / 미납 있음 / 납부 완료**(라디오 아님)
  - **미납 있음**: 선택 연도 의무 월 중 한 달이라도 미납이면 표시(일반·부부만, 면제 제외). 헬퍼 `memberHasAnyUnpaidMonthInYear`
  - **납부 완료**: **1월 ~ 사용자가 고른 달까지** 의무 월 중 모두 납부한 회원만 표시. 드롭다운 `N월까지`. 헬퍼 `memberFullyPaidThroughMonth(member, N)`. 연도 변경 시 기준 달은 당해 연도면 이번 달, 아니면 12월로 초기화
  - 휴회 월은 "의무 없음"으로 표시 — 미납/납부완료 판정에서 제외
  - 상세 기획·스펙: `./기능/입금내역-정렬-필터-기획.md` §8
- **차기월 추천(휴회/병가 반영)** – 확정 모달의 "차기월(권장)"과 기본 선택값이 백엔드에서 휴회·탈퇴를 제외한 다음 의무월로 계산되어 내려옴
  - PaymentRecord 응답에 `nextSuggestedYearMonth` 필드 추가, 회원의 `feeObligationStartAt` + `MemberLeave` 반영
  - 다중 매칭(부부 등) 시 가장 이른 차기 의무월 채택
  - 상세 기획·스펙: `./기능/입금내역-차기월-추천-휴회반영.md`
- **차기월(권장) 사유 표시** – 확정 모달에서 차기월이 단순 `lastPaid + 1`이 아닐 때 그 사유를 라벨로 노출
  - PaymentRecord 응답에 `nextSuggestedReasons: string[]` 필드 추가 (백엔드 `explainNextObligatedMonth` 사용)
  - 사유 예: `2026년 3~4월 휴회 제외`, `의무 시작월: 2026년 4월`, `2026년 5월 탈퇴로 더 이상 의무 없음`
  - 단순 +1 케이스에서는 reasons가 빈 배열이라 사유 라인 자체를 숨김
  - 탈퇴로 차기월이 null인 경우 `차기월(권장): 없음` + 사유 라인
  - 상세 기획·스펙: `./기능/입금내역-차기월-사유-표시.md`
- **매칭 후보 회원 조회(거래일 시점 기준)** – 입금 처리/업로드 화면의 회원 드롭다운이 거래일 범위 시점에 활동 중이던 회원만 노출
  - 조건: `status ∈ {APPROVED, LEFT}` + `leftAt ≥ from` + `feeObligationStartAt ≤ to`
  - LEFT 회원은 회색 톤 + `탈퇴 YYYY-MM` 배지로 구분
  - 운영자가 "탈퇴 처리 전 입금 처리" 순서를 의식할 필요 없음
  - 누적 회원이 1,000명+이어도 응답이 그 시점 활동자로 자동 한정
  - 상세 기획·스펙: `./기능/입금처리-매칭후보-회원-조회.md`

## 3. 핵심 플로우

1. **엑셀 업로드** → 이미 올라온 거래를 빼고 판정(분류 → 매칭 → 계획)한 뒤 PaymentUploadBatch + PaymentRecord + `matchedMembers`를 한 트랜잭션으로 저장
   - 회비가 아닌 건은 그 분류의 건너뜀(SKIPPED), 회원을 못 찾은 회비는 대기(PENDING), 그 밖의 회비는 매칭됨(MATCHED)
2. **업로드 직후** → 요약에서 "N건 일괄 확정" 또는 "검토 필요 N건 보기"
3. **검토·수정** → 상세 시트에서 회원·납부월·분류·회비가 아닌 금액·메모를 고친다. 고치면 검토 사유가 다시 계산된다
4. **확정** → 선택 연도·월로 MembershipPayment 생성, 상태 CONFIRMED
5. **일괄 확정** → 매칭된 회비 중 검토가 필요 없는 건을 거래일 순으로 확정. 검토가 필요한 건은 실패 사유와 함께 남는다
6. **확정 취소** → MembershipPayment 삭제(초과 입금 표시도 되돌림), 상태 MATCHED로 복귀
7. **건너뛰기** → 상태 SKIPPED, 필요 시 unskip으로 복귀 (회비 분류만. 회비가 아닌 건은 분류를 회비로 바꾼다)
8. **일괄 건너뛰기 / 일괄 해제 / 분류 변경** → 탭별로 체크박스 선택 후 처리

## 4. 주요 데이터 모델

- **PaymentUploadBatch**: clubId, uploadedById, fileName, recordCount — 엑셀 업로드 단위
- **PaymentRecord**: batchId, depositorName, amount, memo, matchedMemberId, status, matchedMembers(다중)
  - `kind`(FEE·JOINING_FEE·EVENT·OTHER·INTEREST), `kindReason`(분류 근거)
  - `nonFeeAmount`, `nonFeeKind`(JOINING_FEE·EVENT·OTHER·OVERPAY) — 한 입금에서 회비가 아닌 금액과 그 성격
  - `monthHints` — 입금자가 적은 달
  - `needsReview`, `reviewReason` — 사람이 확인해야만 풀리는 검토 표시와 사유: 이름이 비슷한 회원, 동명이인, 행사비일 수 있는 금액 (금액·월의 검토 사유는 저장하지 않고 조회 때 계산)
  - `note` — 재무 메모 (`memo`는 통장의 메모 원문)
- **PaymentRecordMatchedMember**: paymentRecordId, clubMemberId (다대다 매칭)
- **MembershipPayment**: clubMemberId, year, month, amount, period(MONTHLY·ANNUAL), paymentRecordId, confirmedById
  - 같은 회원·같은 달에 두 건이 있을 수 있다 (부족분을 나중에 채운 경우)
- **FeeType**: 회비 유형 (일반, 부부 등)
- **FeeRate**: 유형별 연도·주기별 금액
- **MemberFeeType**: 회원별 유형 지정 (1인 1유형)
- **CoupleGroup/CoupleMember**: 부부 그룹 관리 (현재 시점)
- **CoupleHistory**: 부부 관계 이력 (거래일 기준 부부 단가 판정용 — 한쪽 탈퇴/해체 후 과거 record 처리 보장). 자세한 내용은 [부부 이력 도입](../부부%20회원%20관리/기능/부부-이력-도입.md)
- **FeeExemption**: 연도별 면제 (사유 포함)
- **MemberLeave**: 휴회 기간 (startYear/startMonth ~ endYear/endMonth, null=장기)
- **ClubMember.feeObligationStartAt**: 회비 의무 시작 시점

## 5. 추가 작업 시 참고

- **단가 판정은 `feeAmountResolver`만 한다.** 업로드·단건 확정·일괄 확정에 단가 계산을 따로 두지 않는다. 한 건의 계획은 `planRecord`, 여러 건의 조회용 계획은 `attachPlans`
- **배정할 달·검토 사유는 응답의 값을 쓴다.** `suggestedSelections`, `needsReview`, `reviewReasons`는 조회할 때 계산된 것이다. DB의 `needsReview`만 보고 판단하지 않는다
- **납부를 만드는 곳은 `applyPlan` 하나다.** 트랜잭션 안에서 회원 행을 잠그고 그 달이 아직 비어 있는지 다시 본다. DB에는 같은 회원·같은 달의 unique가 없으므로(부족분 충당 허용), 다른 경로로 `MembershipPayment`를 만들면 중복을 막을 것이 없다
- **거래일시·거래월은 `kst.ts`로 읽는다.** `date.getMonth()`를 쓰면 서버(UTC)에서 매월 1일 0~9시 입금이 전달로 읽힌다
- `handleConfirm(recordId, selections)` 시그니처 — 선택이 1개면 `{ year, months }`, 여러 개면 `{ selections }`로 보낸다
- confirm API: matchedMembers 우선, 없으면 matchedMemberId 사용. 건너뛴 건·회비가 아닌 건은 400
- 부부 2명 매칭(동일 부부 그룹 전원): 월 합계는 coupleAmount 1회(세대당); MembershipPayment는 합계 coupleAmount가 되도록 인원 수로 균등 분배
- **부부 단가 판정**은 거래일 기준 `CoupleHistory` 우선, `CoupleGroup` fallback. 한쪽 탈퇴로 부부 그룹이 사라진 과거 record도 거래일이 부부 active 구간이면 자동으로 부부 단가 적용 — 자세한 내용은 [부부 이력 도입](../부부%20회원%20관리/기능/부부-이력-도입.md)
- **세대(부부) 단가는 두 명이 함께 매칭됐을 때만 적용한다.** 부부 그룹에 속했다는 이유만으로 한 명의 입금에 세대 단가를 적용하지 않는다(본인 몫만 내는 입금이 매달 "부족"으로 잡힌다). 배경은 [`./기능/일괄확정-부부-단가-거래일-의무-검증.md`](./기능/일괄확정-부부-단가-거래일-의무-검증.md) — 그 문서의 `coupleRateResolver` 모듈은 `feeAmountResolver`로 합쳐졌다
- **운영자가 부부 두 명을 직접 매칭한 record는 거래일 의무 검증을 우회**해 부부 단가로 인정 (D안). 4월 말에 5월 부부 회비를 미리 입금하는 정상 운영 케이스 대응. 발동 조건은 "매칭 인원 정확히 2명 + 그 둘이 부부 이력 또는 부부 그룹에 한 쌍으로 등록"
- 다중 연도·월 선택: `selections` 배열로 (예: 2025년 12월 + 2026년 1월 동시 확정)
- **일괄 API를 더할 때**는 `.claude/rules/bulk-action-pattern.md`를 따른다
- **판정 규칙을 바꾸면** `src/lib/membership-fee/pipeline.regression.test.ts`(가짜 통장 한 벌)로 어느 패턴이 달라지는지 본다

## 6. 입금 부족/초과·합산 입금 처리

| 경우 | 업로드 때 | 확정 때 |
| --- | --- | --- |
| 한 달 단가보다 적게 냄 | 매칭됨 + 검토 필요("입금 부족") | 개별 확정에서 달을 골라 부족 확정(금액 균등 배분). 일괄 확정에서는 빠진다 |
| 부족분을 나중에 채움 | 금액이 앞서 덜 낸 달을 정확히 채우면 사유에 그 달을 알려 준다 | 상세 시트의 "부족분 채우기"로 같은 달에 두 번째 납부를 만든다 |
| 단가의 배수보다 더 냄 | 매칭됨 + 검토 필요("초과 입금 N원") | 고른 달만큼 확정하고 남는 금액은 초과 입금으로 기록. 확정을 취소하면 되돌린다 |
| 가입비 + 회비를 한 번에 냄 (125,000원) | 신규 회원이면 회비 25,000원 + 가입비 100,000원으로 나눠 저장. 기존 회원이면 다섯 달 치 회비 | 나눈 뒤의 회비 금액으로 개월 수를 센다 |
| 회비 + 콕 값 (49,500원) | 매칭됨 + 검토 필요 | 상세 시트에서 "회비가 아닌 금액"과 성격을 적고 적용하면 검토가 풀린다 |
| 연납 금액 (275,000원) | 12개월, 주기 ANNUAL | 월 금액은 연납 금액 ÷ 12 (나머지는 앞 달부터 1원씩) |

- 배경과 결정은 [`./기능/자동-분류-월힌트-단가통일.md`](./기능/자동-분류-월힌트-단가통일.md).
