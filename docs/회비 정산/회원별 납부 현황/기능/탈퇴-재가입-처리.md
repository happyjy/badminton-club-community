## 1. 배경 (Why)

- **탈퇴했다 돌아온 회원은 매번 DB를 손으로 맞춰야 했다.**
  - 클럽 회원 기록은 클럽·사용자마다 하나라, 탈퇴한 사람이 앱에서 다시 가입 신청하면 "이미 가입된 클럽입니다"로 막힌다. 재가입은 관리자가 회원 관리에서 상태를 탈퇴 → 승인됨으로 바꾸는 방법뿐이다.
  - 되돌리면 탈퇴일은 지워졌지만 회비 시작월은 예전 값 그대로라, 떠나 있던 기간이 모두 미납이 됐다.
  - 운영(main)에서는 탈퇴일도 지워지지 않아, 회원 E·회원 F는 승인 회원인데 예전 탈퇴일이 남아 입금 자동 매칭에서 빠졌다. 2026-11에 세 명(회원 E·회원 F·회원 G)을 손으로 맞췄다.
- **탈퇴 처리도 같은 문제를 만들었다.**
  - 상태를 탈퇴로 바꾸면 탈퇴일이 오늘로 들어갔다.
  - 몇 달 안 내다 정리한 회원은 그 사이가 미납으로 남아 납부율만 낮췄다. 클럽은 그만둔 사람에게 밀린 회비를 받지 않는다. 그래서 탈퇴월은 마지막으로 회비를 낸 달로 두기로 했다(2026-11-22 사용자 결정).

## 2. 도입한 개선

- **회원 관리 상세 시트에서 상태를 바꿀 때, 두 경우에만 달을 묻는 시트가 겹쳐 뜬다.**

| 이전 → 다음 | 시트 | 칸의 기본값 | 저장 |
| --- | --- | --- | --- |
| 탈퇴 아님 → 탈퇴 | 탈퇴 처리 · 탈퇴월 | 마지막으로 회비를 낸 달 | 상태, 탈퇴일 = 그 달 1일 |
| 탈퇴 → 승인됨·휴가중 | 다시 가입 처리 · 다시 시작하는 달 | 새 가입 규칙(15일까지 그 달, 16일부터 다음 달) | 상태, 탈퇴일 지움, 시작월 = 그 달 1일 |
| 그 밖 | 없음 | — | 지금처럼 상태만 바꾸고 탈퇴일을 지운다. 탈퇴 → 탈퇴는 탈퇴일을 둔다 |

- 탈퇴 시트의 안내: "마지막으로 회비를 낸 달입니다."(칸 값이 그 달일 때), "낸 회비가 없습니다."(낸 회비가 없을 때), "이 달까지 회비를 내야 하는 달로 봅니다."
- 다시 가입 시트의 안내: "이 달부터 회비를 냅니다.", "실수로 탈퇴 처리했다면 예전 시작월(YYYY-MM)을 고르세요."(예전 시작월이 기본값과 다를 때)
- [취소]하면 아무것도 바뀌지 않는다.
- **"탈퇴일은 탈퇴 상태에만 있다"를 저장하는 두 API에서 지킨다.**
  - 그래서 탈퇴일을 읽는 곳(입금 매칭·확정 계획·납부월 이월)은 상태를 다시 보지 않아도 맞다.

## 3. 설계 의사결정

| 결정 | 이유 | 버린 대안 |
| --- | --- | --- |
| 예전 회원 기간의 이력은 남기지 않는다 | 재가입한 사람은 지금까지 3명이고 예전 기간이 대부분 2025년 이전이다. 재무 표는 해마다 새로 만든다 | 회원마다 가입~탈퇴 기간을 여러 개 저장 — 회비를 계산하는 모든 곳이 기간 목록을 읽어야 한다 |
| 상태를 바꾸는 순간에 달을 묻는다 | 그때 정해야 손으로 고칠 일이 다시 생기지 않는다 | 서버가 기본값으로 넣고 알림만 — 넘어가면 틀린 달이 남는다 |
| | | 회원 상세에 처리 버튼 따로 — 상태를 바꾸는 곳이 두 군데가 된다 |
| 탈퇴한 사람이 앱에서 다시 신청하는 길은 만들지 않는다 | 실제로도 관리자가 상태를 되돌려 돌아왔다 | 탈퇴 기록을 대기중으로 되돌리는 재신청 |
| 탈퇴일을 읽는 곳을 고치지 않고 쓰는 곳에서 약속을 지킨다 | 읽는 곳이 여섯 군데라 하나라도 빠지면 어긋난다. 쓰는 곳은 두 군데다 | 읽는 곳마다 "탈퇴 상태일 때만" 조건 추가 |
| 이전 상태는 서버가 DB에서 읽는다 | 화면이 보낸 이전 상태를 믿으면 두 관리자가 동시에 바꿀 때 어긋난다 | 요청에 이전 상태를 실어 보냄 |
| 예전 시작월을 안내로 보인다 | 실수로 탈퇴 처리한 뒤 되돌리면 예전 시작월이 사라져 지난 달들이 해당없음이 된다 | 안내 없음 |
| 탈퇴 전 납부의 "이월 필요" 경고는 코드로 막지 않고 이 문서에만 적는다 (2026-11-25 사용자 결정) | 2026-11-25 운영 DB에 해당 회원이 없다. 실제로 생기면 다시 가입한 달을 회원에 저장하는 방법으로 고친다 | 다시 가입한 달을 회원에 저장해 그 달 전 납부를 경고에서 뺌 — DB 칸과 마이그레이션이 는다 |
| | | 시작월 전 납부에는 이월 버튼을 숨김 — 시작월이 실제보다 늦게 들어간 회원의 이월까지 막힌다 |

- **대가**: 돌아온 회원의 예전 기간은 기록에 남지 않는다.
  - 지난 해 표에서 예전 기간이 해당없음(회색)으로 나오거나 줄이 빠진다.
  - 탈퇴 전에 낸 회비는 "의무 없는 달의 납부"가 되어 대시보드에 "납부 있음 — 이월 필요"가 뜨고, 회원 상세에 [다음 의무월로 이월]이 보인다. 이 이월은 누르지 않는다(누르면 탈퇴 전 납부가 돌아온 뒤 달로 옮겨진다). 2026-11-25 운영 DB에는 해당 회원이 없다.

## 4. 백엔드 처리

- **`PUT …/members/[userId]/status`** `{ status, leftMonth?, feeStartMonth? }`
  - 대상 회원을 읽어(없으면 404 "회원을 찾을 수 없습니다") `statusMonthKind(이전, 다음)`으로 나눈다.
  - 탈퇴: `leftMonth`가 `YYYY-MM`이 아니면 400 "탈퇴월을 골라주세요".
  - 다시 가입: `feeStartMonth`가 `YYYY-MM`이 아니면 400 "다시 시작하는 달을 골라주세요".
  - 달은 그 달 1일 00:00 UTC로 저장한다.
- **`GET …/members/[userId]/status-defaults`** → `{ lastPaidMonth, rejoinStartMonth, previousStartMonth }`
  - `lastPaidMonth`: 그 회원의 모든 납부(통장 입금·직접 추가, 미리 낸 달 포함) 중 연·월이 가장 늦은 달. 없으면 null.
  - `rejoinStartMonth`: `defaultFeeObligationStartAt(오늘)`. 가입(`join.ts`)과 같은 함수다.
  - `previousStartMonth`: 지금 저장된 시작월. 날짜를 달로 바꿀 때 한국 시각으로 읽는다(예전 값 중 한국 자정으로 저장된 것이 있다).
- **`PATCH …/members/[userId]/fee-obligation`**
  - 탈퇴가 아닌 회원에 탈퇴일 값을 보내면 400 "탈퇴한 회원만 탈퇴일을 넣을 수 있습니다". `null`은 받는다(회원 상세 화면이 늘 보낸다).
  - 탈퇴 회원의 탈퇴일을 `null`로 보내면 400 "탈퇴월을 입력해주세요".

## 5. 프런트 처리와 UX 디테일

- `MembersView`가 상태 고르기에서 두 경우를 가려 `onLoadStatusDefaults`로 기본값을 불러온 뒤 `MemberStatusMonthSheet`를 연다. 열 때마다 `key`를 바꿔 칸을 기본값으로 다시 채운다.
- 달 시트는 상세 시트 안에 둔다. Headless UI가 겹친 시트로 다뤄, 달 시트를 누를 때 상세 시트가 닫히지 않는다.
- 기본값을 못 불러오면 빈 칸으로 열고, 칸이 비어 있으면 저장 버튼이 잠긴다.
- `useMemberActions.changeStatus`는 고른 달을 함께 보내고, 실패하면 서버가 준 사유를 토스트로 보인 뒤 목록을 되돌린다.
- 회원 상세(`/clubs/[id]/members/[userId]`)에서 탈퇴 회원의 탈퇴일을 비우고 저장하면 서버 사유 "탈퇴월을 입력해주세요"를 토스트로 보인다(2026-11-26부터. 전에는 "저장에 실패했습니다."만 보였다).
- 미리보기: `/dev/admin-preview?screen=member-status-month`(`&kind=rejoin`).
