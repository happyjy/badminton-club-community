## 1. 배경 (Why)

- **재무의 표는 완납인데 회비 통장에는 입금이 없는 달이 있다.**
  - 회원 A 2026-09: 회비를 실수로 콕 계좌로 보냈다. 회비 통장으로 옮길 계획은 없고, 낸 것으로 채우기만 한다.
  - 회원 B 2026-10·11: 재무 표는 완납인데 통장 입금이 없다.
- **앱에는 통장 입금 없이 납부를 넣을 길이 없었다.**
  - 납부(`MembershipPayment`)는 반드시 입금 내역(`PaymentRecord`)에 묶였고, 입금 내역은 업로드로만 생긴다.
  - 목표가 "앱만으로 재무 표를 그대로 따라 하기"라서 DB를 직접 고치지 않고 기능으로 만든다.

## 2. 도입한 개선

- **회원 상세에 "직접 추가한 납부" 목록과 [납부 직접 추가] 버튼을 둔다.**
  - 시트에서 연월·금액·사유를 넣는다. 연월을 고르면 그 달의 기본 금액을 채운다(고칠 수 있다).
  - 사유는 "다른 계좌로 보냄", "현금으로 받음", 기타(직접 쓴 글, 100자까지) 가운데 하나다.
  - 목록 한 줄: `2026.09 · 25,000원 · 다른 계좌로 보냄`. 누르면 넣은 날·넣은 사람이 보이고 지울 수 있다.
- **납부 현황 칸·월별 납부율·미납자 목록·내보낸 엑셀에서는 완납이다.**
  - 재무의 표와 같다.
- **대시보드의 "YYYY년 총 수입"에는 넣지 않는다.**
  - 총 수입과 월별 금액은 통장 입금에 묶인 납부만 더한다. 통장 잔액과 맞게 하기 위해서다.
  - 직접 추가가 있으면 총 수입 아래에 "직접 추가 3건 · 75,000원 (총 수입에 넣지 않음)"을 따로 적는다.
  - 리포트 화면의 "총 수입"도 같은 값(통장 입금만)이다.

## 3. 설계 의사결정

| 결정 | 이유 | 버린 대안 |
| --- | --- | --- |
| 납부의 입금 칸(`paymentRecordId`)을 비울 수 있게 하고 `manualReason`을 더한다 | 납부를 읽는 곳(현황·내보내기·미납·확정 계획·이월)이 그대로 완납으로 본다. 입금 쪽 화면에는 나타나지 않는다 | 가짜 입금 기록 — 업로드 배치가 꼭 있어야 하고 입금 내역 목록·최근 업로드·최신 거래일·업로드 중복 검사에 섞인다 |
| | | 별도 테이블 — 납부를 읽는 곳마다 두 테이블을 합쳐야 한다 |
| 이름은 "납부 직접 추가" | 다른 계좌·현금 등 까닭이 여러 가지라 이름에 까닭을 넣지 않는다 | "통장 밖 납부" |
| 한 번에 한 달 | 회원 B는 두 번 넣으면 된다. 기간으로 받으면 달마다 금액 처리가 복잡해진다 | 시작~끝 기간 |
| 이미 납부가 있는 달, 의무가 없는 달(가입 전·휴회·탈퇴 후), 면제 달은 막는다 | 같은 달이 두 번 잡히거나 이월할 납부가 생기는 것을 막는다 | 경고만 하고 넣기 |
| 기본 금액은 그 해 월 단가, 그 달에 부부였으면 부부 월 단가의 반 | 입금 확정이 부부 입금을 두 사람에게 나누는 방식과 같다 | 금액을 비워 둠 |
| 수정 없이 지우고 다시 넣는다 | 드물게 쓰는 기능이라 단순하게 둔다 | 수정 시트 |
| 직접 추가는 그 화면의 삭제로만 지운다. 입금에 묶인 납부는 이 API로 지우지 않는다 | 입금에 묶인 납부는 입금 내역 화면의 확정 취소로 지운다 | 하나의 삭제 API |
| DB CHECK 제약 없이 API가 "입금 없음 ⇒ 사유 있음"을 지킨다 | Prisma 스키마로 나타낼 수 없어 `migrate diff`의 드리프트 확인과 어긋난다 | CHECK 제약 |

## 4. 백엔드 처리

- **스키마**: `MembershipPayment.paymentRecordId String?`, `paymentRecord PaymentRecord?`, `manualReason String?`.
- **`GET …/manual-payments`**: 그 회원의 `paymentRecordId = null` 납부를 최근 달부터. 넣은 사람 이름은 `confirmedById`로 회원을 한 번 더 읽어 붙인다.
- **`POST …/manual-payments`** `{ year, month, amount, reason }`
  - zod(`manualPaymentSchema`) 실패는 400. 금액이 정수 1 이상이 아니면 "금액을 확인해주세요", 사유가 비면 "사유를 입력해주세요".
  - 트랜잭션 안에서 회원 행을 잠그고(`SELECT … FOR UPDATE`, 입금 확정과 같다) 휴회·면제·그 해 납부를 읽어 `manualPaymentBlockReason`으로 다시 검사한다.
  - 막히면 400: "이미 납부가 있는 달입니다", "회비 의무가 없는 달입니다", "면제 기간인 달입니다".
  - 탈퇴일은 회원이 탈퇴 상태일 때만 본다. 다시 돌아온 회원의 예전 탈퇴일은 막지 않는다(`memberYearStatus`와 같다).
  - 저장: `paymentRecordId: null`, `manualReason: reason`, `period: MONTHLY`, `confirmedById: 넣은 관리자`.
- **`DELETE …/manual-payments/[paymentId]`**: 그 회원의 납부가 아니면 404, 입금에 묶였으면 400 "입금으로 확정된 납부는 여기서 지울 수 없습니다". 지울 때도 `paymentRecordId: null` 조건을 다시 건다.
- **`GET …/manual-payments/suggest?year=&month=`**: `feeRateSettingsFromTypes`의 그 해 단가와 `wasCoupleAt(그 달 1일)`로 `{ amount, isCouple }`. 그 해 단가가 없으면 `amount: null`.
- **대시보드**: `loadMemberYearData`가 납부를 읽을 때 `paymentRecordId`도 읽는다. 없으면 `manualPayments`(건수·금액)에 더하고 `amountsByMonth`에는 넣지 않는다. 납부 달에는 둘 다 넣는다. 응답의 `summary.manualPayments`.
- **바꾸지 않아도 맞게 도는 곳**
  - 입금 확정 계획(`confirmPlanner`): 기존 납부를 모두 읽으므로 뒤에 온 입금은 직접 추가한 달을 건너뛴다.
  - 휴회 등록·이월(`findOrphanPayments`, `payments/shift`): 납부 행 단위라 똑같이 다룬다.
  - 확정 취소·업로드 배치 삭제: 입금에 묶인 납부만 지운다.

## 5. 프런트 처리와 UX 디테일

- `ManualPaymentSection`이 목록과 두 시트(추가, 내용·삭제)를 그린다. 휴회 목록·시트와 같은 모양이다.
- 연월·금액·사유가 다 차야 [저장]이 눌린다. 기타를 고르면 글 칸이 나온다.
- 실패하면 서버가 준 사유를 토스트로 보이고 시트를 열어 둔다.
- [삭제]는 "이 납부를 지울까요?"로 한 번 더 묻는다.
- 넣거나 지우면 대시보드 캐시(`paymentDashboard`)를 비운다.
