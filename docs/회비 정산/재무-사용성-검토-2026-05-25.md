# 재무 사용성 검토 (2026-05-25)

회비 정산 기능을 재무 담당자가 실제 운영 흐름에서 사용한다고 가정했을 때 부딪힐 어려움을 정리한다. 직접 테스트 전에 우선순위 높은 시나리오를 확인하기 위한 체크리스트로 활용한다.

---

## P0 — 잘못된 결과가 조용히 만들어질 수 있는 곳

### 1. 일괄 확정의 동시성 race (중복 납부 기록 위험)

- **시나리오**: 두 관리자가 같은 record들을 비슷한 시점에 일괄 확정. 또는 한 명이 새로고침 없이 두 번 클릭.
- **위치**: `src/pages/api/clubs/[id]/membership-fee/records/bulk-confirm.ts:433-459`. record별 `$transaction` 안의 `paymentRecord.update` where 절에 `status: 'MATCHED'` 조건이 **빠짐** (다른 bulk-\* 핸들러는 다중 안전망 룰을 따르는데 여기만 누락).
- **결과**: 같은 month/clubMemberId로 `MembershipPayment` 두 건 생성 → 대시보드 집계 중복.
- **재무가 알아챌까**: 거의 못 알아챔. 대시보드 합계만 보면 정상으로 보일 수 있음.
- **권장**: `where: { id, status: 'MATCHED' }`로 가드. 0건 업데이트면 "이미 처리됨" 분기.

### 2. 1인 매칭에 부부 단가 폴백 (D안 가드 우회)

- **시나리오**: 부부 그룹에 속한 한 명이 단독 입금. 배우자가 거래일에 의무 상태이긴 함.
- **위치**: `src/lib/membership-fee/coupleRateResolver.ts:186-204` 폴백. D안 강화는 `memberIds.length === 2` 명시 매칭에만 적용되고, 폴백 경로는 1인이어도 `groupPartnerObligated && isObligatedAtTx(mid)`면 부부 단가 부여.
- **결과**: 일반 단가로 들어와야 할 입금이 부부 세대 단가로 검증돼 "부족/초과" 오류, 또는 의도 다른 확정.
- **권장**: 폴백에서도 `memberIds.length === 1`이면 일반 단가만 허용.

### 3. 업로드 단계와 확정 단계의 부부 판정 불일치 (2-pass 검증 어긋남)

- **시나리오**: 업로드 시 `upload.ts`는 현재 `CoupleGroup`만 보고 부부 여부를 판정, 확정 시 `bulk-confirm`은 거래일 `CoupleHistory`로 정확히 판정. 거래일 ≠ 현재 부부 상태인 record(예: 4/29 입금인데 부부 history가 5/1 시작)가 발생.
- **위치**: `src/pages/api/clubs/[id]/membership-fee/upload.ts:154-212, 274-289` / `bulk-confirm.ts`가 `resolveMonthlyAmount` 사용.
- **결과**: 업로드 단계에서 MATCHED로 들어왔다가 일괄 확정에서 검증 실패. 재무는 "어제까지 멀쩡하던 게 왜?" 혼란.
- **권장**: 업로드 단계에서도 `coupleHistories`를 함께 로드해 같은 판정 함수를 통과시킴.

### 4. FeeRate 변경 시점 vs 거래일 정렬 누락

- **시나리오**: 연중에 단가가 바뀌면(2025-06부터 25,000 → 30,000), 5월 입금이 6월 단가로 검증됨.
- **위치**: `bulk-confirm.ts:79-113` — `year` 기준으로만 FeeRate 조회, `transactionDate` 기반 구간 매칭 없음.
- **결과**: "금액 배수 안 맞음" 오류, 또는 잘못된 단가로 확정.
- **권장**: FeeRate에 적용 시점 필드 도입 + transactionDate 기준 조회. 당장 어렵다면 단가 변경이 있는 해는 "단가 변경 안내 배너".

## P1 — 재무가 매번 헛수고하게 되는 흐름

### 5. 일괄 확정 실패 시 어느 건이 실패했는지 모름

- **시나리오**: 50건 선택 → 일괄 확정 → 토스트 "부족 입금 1건으로 실패". 그 1건이 누군지 모름.
- **위치**: `bulk-confirm.ts` 응답에 실패 record 목록 누락 (반면 bulk-unconfirm/skip은 `results.failed` 형식 따름).
- **권장**: `.claude/rules/bulk-action-pattern.md`의 표준 `results: { success, failed: [{recordId, reason}] }` 응답 형식으로 통일. 호출부에서 실패 row 하이라이트.

### 6. 자동 매칭 신뢰도가 화면에 안 보임

- **시나리오**: 입금자명 "김철수"가 성-생략 매칭(confidence 0.7)으로 자동 매칭됐는데, 정확 매칭과 시각적으로 동일.
- **위치**: `src/lib/membership-fee/memberMatcher.ts`는 `matchType`/`confidence` 산출하지만 `PaymentRecordTable.tsx`에서 노출 안 함.
- **권장**: confidence < 0.9면 ⚠️ 배지 + 호버 시 매칭 사유. 부부 자동 추가(`maybeAttachSpouse`)된 경우도 "자동 추가" 표시.

### 7. 금액 부족/초과가 확정 모달을 열어야 보임

- **시나리오**: 50,000원 입금(예상 45,000)이 "초과"인지 업로드/처리 테이블에서 안 보임. 확정 모달까지 가야 알 수 있음.
- **위치**: `PaymentRecordTable.tsx`의 금액 컬럼이 검증 결과 미표시.
- **권장**: 테이블 금액 칸에 "부족/초과/일치" 배지. 호버 시 "예상 45,000 / 입금 50,000".

### 8. 차기월 추천 사유가 모호

- **시나리오**: 자동 추천 월이 휴회·가입 시점·탈퇴 때문에 뛰어 있음. 재무는 왜 그 월이 나왔는지 모름.
- **위치**: API 응답엔 `nextSuggestedReasons`가 있는데 UI에서 분명히 안 보임.
- **권장**: 권장 월 옆 ⓘ 아이콘 + 호버 시 사유 라인별 표시 ("∙ 2월: 의무 시작 3월부터 ∙ 4월: 휴회 기간").

### 9. 사용자 지정 월 수 ≠ 금액 기준 월 수일 때 묵묵히 재분배

- **시나리오**: 75,000원 입금(3개월치)인데 재무가 2개월만 선택 → 월당 37,500원으로 분배. 비정상 단가가 DB에 그대로 들어감.
- **위치**: `bulk-confirm.ts:351-357` — 검증 없이 통과.
- **권장**: 월 수 불일치는 에러로 거부하거나, "선택 월 수가 입금액과 안 맞습니다 (예상 3개월)" 명시적 경고 + 확인 단계.

## P2 — 운영 안전망

### 10. batch 삭제로 확정 30건이 한 번에 사라짐

- **시나리오**: 50건 batch 중 30건 확정한 상태에서 삭제 클릭 → 경고는 있지만 한 번에 다 날아감, 되돌리기 불가.
- **위치**: `src/pages/clubs/[id]/membership-fee/process.tsx:297-315`.
- **권장**: 확정 건 1개 이상이면 삭제 버튼 비활성화 + "먼저 확정 취소 후 재시도" 안내. 또는 "미확정 건만 삭제" 옵션.

### 11. skip → unskip 시 원래 상태 복구 불가

- **시나리오**: ERROR였던 record를 skip → unskip → MATCHED로 고정 복구. "왜 처음에 ERROR였는지" 사유 묻힘.
- **위치**: `src/pages/api/clubs/[id]/membership-fee/records/bulk-unskip.ts`가 status를 'MATCHED' 고정 설정.
- **권장**: `statusBeforeSkip` 컬럼 추가 또는 unskip 시 검증 재실행.

### 12. 확정 → 미확정 시 대시보드 차기월 권장이 stale

- **시나리오**: 미확정으로 되돌렸는데 대시보드의 "차기 의무월" 권고는 캐시 그대로.
- **위치**: `bulk-unconfirm.ts` 응답이 영향받은 회원 정보를 안 줌.
- **권장**: 미확정 직후 `paymentDashboard` 외 회원별 상세까지 invalidate.
