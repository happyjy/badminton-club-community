# 부부 이력 도입 — 거래일 기준 부부 단가 판정

> 도입 시점: 2026-05-09
> 관련 화면: [부부 회원 관리 컨텍스트](../부부회원관리-컨텍스트.md), [입금 내역 처리 컨텍스트](../../입금%20내역%20처리/입금내역-처리-컨텍스트.md)

## 배경 (Why)

`CoupleGroup`은 "지금 시점의 부부"만 표현한다. 한쪽이 탈퇴하거나 해체되면 그룹 데이터가 삭제(cascade)되고, 그 시점 이전의 부부 관계가 사라진다.

문제는 **과거 거래일의 입금**이다. 한쪽이 5월에 탈퇴해 부부 그룹이 사라진 회원이 1~3월에 부부 단가(예: 45,000원)로 입금한 record가 시스템에 남아 있을 때, 일괄 확정 로직은 "현재" 회원 한 명만 보고 일반 단가(예: 30,000원)로 계산한다. 그러면:

- `45,000 % 30,000 ≠ 0` → "입금 부족" 사유로 일괄 확정 실패
- 운영자가 매번 개별 확정 화면에서 월 선택+부족 확정으로 우회 처리
- 휴먼 에러 가능성 ↑, 처리 시간 ↑

부부 그룹 데이터를 보존하면 해결되지만, "현재 부부"만 표현하던 기존 모델 의미가 흐려진다. 그래서 등록·해체 시점을 누적하는 별도 이력 테이블을 도입했다.

## 도입한 개선 (What)

### 1) `CoupleHistory` 모델 신설

```prisma
model CoupleHistory {
  id                  Int       @id @default(autoincrement())
  clubId              Int
  clubMemberId        Int       // 본인
  partnerClubMemberId Int       // 배우자
  startedAt           DateTime  // 부부로 등록된 시점
  endedAt             DateTime? // 해체 시점. null이면 현재 진행 중
  createdAt           DateTime  @default(now())
}
```

- 같은 (self, partner) 쌍이 여러 번 active일 수 있음 → **재결합 표현 가능**
- 한 회원의 active(endedAt=null) row는 비즈니스 로직으로 동시 1건 보장 (등록 시 기존 active row 종료)

### 2) 거래일 기준 부부 판정 헬퍼

`src/lib/membership-fee/coupleHistory.ts`

```ts
export function wasCoupleAt(
  clubMemberId: number,
  transactionDate: Date,
  histories: CoupleHistoryRow[]
): { isCouple: true; partnerId: number } | { isCouple: false };
```

- 거래일이 `[startedAt, endedAt]` 범위에 있는 row를 active로 인정
- 활성 row가 없으면 부부 아님

### 3) 등록·해체 API 동기화

| API                                        | 변경                                                                                                   |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| `POST /membership-fee/couples`             | 트랜잭션 안에서 잔여 active row 종료 → `CoupleGroup` 생성 → `CoupleHistory` 양방향 row 생성 (A→B, B→A) |
| `DELETE /membership-fee/couples/[groupId]` | 트랜잭션 안에서 멤버의 active `CoupleHistory.endedAt=now()` → `CoupleGroup` 삭제                       |

### 4) 입금 확정 단계 판정 로직 변경

부부 단가 판정 우선순위:

1. **`CoupleHistory` (거래일 active)** — 과거/현재 모두 정확
2. **`CoupleGroup` (현재)** — 이력이 없는 과거 데이터 fallback (백필 누락 보호용)

#### `bulk-confirm.ts`

- record별 거래일에 active인 이력으로 `coupleCandidateIds = [self, partner]` 산출
- 거래일에 의무인 멤버만 추려 `effectiveCoupleMemberIds` 결정
- 매칭된 `memberIds`가 effective 집합과 정확히 일치하면 세대당 단가(`coupleAmount`) 분배
- 일치하지 않으면 회원별 일반/부부 단가 합산 (이력 또는 그룹 어느 쪽이라도 부부면 부부 단가)

#### `records/[recordId]/confirm.ts`

- 회원 단가 판정도 거래일 기준 이력 우선, 그룹 fallback

### 5) 기존 데이터 백필 스크립트

`src/scripts/backfillCoupleHistory.ts`

- 현존 모든 `CoupleGroup` → `CoupleHistory` 양방향 row 생성
- `startedAt = CoupleGroup.createdAt`, `endedAt = null`
- 중복 방지 안전망 포함

### 6) 수동 보정 화면 (2026-05-10 추가)

자동 동기화만으로는 두 가지 운영 케이스를 못 잡는다.

1. **백필 누락 / 자동 등록 이전 시점에 이미 해체된 과거 부부** — 해체 시점에 자동 동기화 코드가 없었다면 이력이 비어 있다
2. **자동 등록 시점이 실제 시점과 다름** — 운영자가 부부 등록을 늦게 누른 경우 startedAt이 실제 결혼 시점이 아니라 운영자 클릭 시점이 된다

이를 보정하기 위해 부부 회원 관리 화면(`/clubs/[id]/membership-fee/settings/couples`)에 이력 CRUD 섹션을 추가했다 (1차 도입). 1차 도입에서는 부부 그룹 섹션과 이력 섹션이 분리되어 있었다.

### 7) 화면 통합 (2026-05-11)

운영자 입장에서 "현재 부부"와 "과거 부부"는 결국 같은 데이터(부부 관계)를 시점만 다르게 본 것이다. 두 섹션이 분리되어 있으면 동일 데이터를 두 군데로 관리해야 해 혼란스럽다. 그래서 화면을 다음과 같이 통합했다.

#### 통합 정책

| 항목 | 정책 |
| --- | --- |
| 정본 | `CoupleHistory` 단일 |
| 화면 목록 | active + ended 모두 한 목록. active는 `[active]` 배지로 구분 |
| 등록 버튼 | 1개. 모달의 "종료된 관계" 체크박스로 active/ended 구분 |
| `CoupleGroup` | 캐시 역할로 격하. history CRUD가 트랜잭션 안에서 자동 동기화 |

#### 자동 동기화 규칙

`src/lib/membership-fee/coupleHistorySync.ts`의 헬퍼가 담당.

| history 변경 | `CoupleGroup` 동작 |
| --- | --- |
| active 추가 | 같은 멤버 쌍 그룹 ensure (없으면 생성, 있으면 그대로) |
| active 수정 (멤버 쌍 변경) | 옛 쌍 그룹 정리 + 새 쌍 그룹 ensure |
| active → ended | 그 쌍의 다른 active row가 없으면 그룹 삭제 |
| ended → active | 새 멤버 쌍 그룹 ensure |
| ended → ended | 그룹 영향 없음 |
| active 삭제 | 그 쌍의 다른 active row가 없으면 그룹 삭제 |
| ended 삭제 | 그룹 영향 없음 |

#### active 충돌 검증

한 회원에게 다른 partner와의 active row가 이미 있으면 등록·수정 모두 거부 (서버 트랜잭션 안에서 검증). 메시지: `"대상 회원이 이미 다른 활성(active) 부부 관계에 속해 있습니다"`.

같은 partner와의 active row가 이미 있는 멱등 등록은 허용 (검증을 통과한다는 의미이며, 새 row가 또 추가되긴 함 — UI에서는 막지 않으니 운영자가 의도한 경우만 사용).

#### 입력 시점 단위

회비 정산이 월 단위라 일자 정밀도가 불필요. UI는 연·월만 받고, 서버에서 다음과 같이 저장:

- `startedAt` = 해당월 1일 00:00:00.000
- `endedAt` = 해당월 마지막 일 23:59:59.999

이 변환은 `lib/membership-fee/coupleHistory.ts`의 `yearMonthToStartedAt`/`yearMonthToEndedAt` 헬퍼가 담당.

#### 결과

- 부부 회원 관리 화면이 `CoupleHistory` 한 곳만 다룸 → 멘탈 모델 단순화
- `CoupleGroup` API는 그대로 유지(다른 화면이 캐시 조회용으로 사용 가능). 단, 부부 회원 관리 화면은 호출하지 않음
- `CoupleManageList` / `CoupleRegisterModal` / `useCouples` 훅은 다른 화면이 사용 중이라면 그대로 두고, 본 화면 코드에서만 import 제거

## 설계 의사결정

### Q1. 양방향 row를 두 개 만드는 이유

```
A↔B 부부 등록 시
 row1: clubMemberId=A, partnerClubMemberId=B
 row2: clubMemberId=B, partnerClubMemberId=A
```

조회 편의가 압도적이다. `wasCoupleAt(A, txDate, histories)`처럼 자기 자신 ID 한 개로 partner를 즉시 얻을 수 있다. 단방향이면 매 조회마다 양쪽 매칭이 필요해 코드 복잡도 ↑.

대칭성 정합성 부담은 등록·해체 API가 트랜잭션으로 두 row를 같이 만들고/같이 닫는 책임을 진다.

### Q2. 왜 `CoupleGroup`을 폐기하지 않았나

- 운영 화면(`/settings/couples`)이 그룹 단위로 표시·관리
- 다른 화면(대시보드 partner 표시 등)이 현재 부부 그룹을 직접 사용 중
- "현재 부부"라는 단순한 표현이 운영 흐름과 자연스럽게 맞음

`CoupleGroup`은 "현재 운영 상태", `CoupleHistory`는 "시간축 이력"으로 책임을 분리.

### Q3. 매칭 단계도 이력 기반으로 전환했는가

이번 PR에서는 **매칭 단계는 손대지 않았다**. 이유:

- 매칭 단계가 `coupleGroups`만 보면 한쪽이 탈퇴해 그룹이 없는 record는 한 명만 매칭됨
- 하지만 이번 변경으로 **확정 단계가 거래일 이력 기반으로 부부 단가 인정** → 한 명 매칭이어도 정상 확정됨
- 매칭 자동 묶기까지 손대면 회귀 위험 ↑ → 후속 PR로 분리

### Q4. 대시보드/미납 계산은 왜 안 바꿨나

대시보드와 unpaid는 "현재 시점 부부 여부"로 미래 미납액을 계산한다. 이건 운영 의도(향후 회비 산정)에 맞으므로 그대로 유지.

## UX 디테일

### 사용자 시각

- (이전) 한쪽 탈퇴한 부부의 과거 record → "입금 부족"으로 일괄 확정 실패 → 개별 확정 우회 필요
- (이후) 동일 record → 거래일이 부부 active 구간이면 자동으로 부부 단가 인정 → 일괄 확정 성공

### 운영자 시각

- 부부 등록·해체 화면 변화 없음
- 데이터만 이력 테이블에 누적

## 마이그레이션·롤아웃 절차

1. `pnpm run build:schema` (소스 schema → schema.prisma 동기화)
2. `npx prisma migrate dev --name add_couple_history` (개발 환경)
3. 운영 배포 시 `prisma migrate deploy`
4. **백필 스크립트 1회 실행:** `npx ts-node src/scripts/backfillCoupleHistory.ts`

백필을 잊으면 그룹은 그대로 남아 fallback이 동작하므로 즉시 회귀는 없지만, "그룹이 사라진 과거 record"의 자동 부부 단가 처리는 백필 이후부터 적용된다.
